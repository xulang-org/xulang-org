并发

xu f(args) 调度一个协程。调度决定哪个就绪任务可以推进；并行是多个任务同时在不同 CPU 线程上执行。启动协程本身既不保证执行顺序，也不承诺 CPU 并行。xu.pkg.f 是包限定调用，不是启动协程。

下列代码块均使用官方 SDK v0.10.12 检查。每个块单独保存为一个 .xu 文件；完整程序用 xu check，仅含函数的示例用 xu check --lib。预期诊断均为实际输出的子串。完整程序也通过本机 xu run；浏览器运行使用下述 WASM 子集。

调度与无缓冲会合

容量为零的信道要求发送方与接收方会合。对开放的空信道接收会等待；缓冲区满时发送也会等待。这些信道等待会让调度器推进其他就绪协程。应通过信道等待结果，再让 main 返回；启动并不代表任务已完成。

@main

fn worker(id int, ch chan int) {
    ch <- id * 10
}
fn main() int {
    ch := chan int{cap: 0}
    xu worker(1, ch)
    println(<-ch)
    << 0
}

预期 xu check：通过。 xu run 输出（逐行）：10.

发送与接收：转移 owned 数据，共享信道句柄

ch <- value 发送，<-ch 接收。发送 owning 值会转移所有权；标量按值复制。信道句柄可以传给工作协程，调用方仍可使用它。引用（包括嵌套在容器内的引用）不能跨越 xu 或信道边界；这并不能保证外部代码中任意共享状态的安全。

@main

fn main() int {
    ch := chan string{cap: 1}
    text := "owned"
    ch <- text
    println(<-ch)
    << 0
}

预期 xu check：通过。 xu run 输出（逐行）：owned.

@main

fn bad() {
    ch := chan string{cap: 1}
    text := "owned"
    ch <- text
    println(text)
}

预期 xu check --lib：失败，诊断包含 use of moved value 'text'.

@main

fn worker(value &int) {}
fn bad() {
    value := 1
    xu worker(&value)
}

预期 xu check --lib：失败，诊断包含 xu argument cannot be a reference type (M17).

Close：先排空缓冲，再接收零值

close(ch) 将信道标记为关闭，不会丢弃缓冲数据。下例的整数信道先返回排队的 7，随后不等待就返回 0。若零是合法数据，不应将它当作唯一结束标记；应定义应用层消息 / 完成协议。在所有发送结束后由唯一关闭方关闭，且只关闭一次。

@main

fn main() int {
    ch := chan int{cap: 1}
    ch <- 7
    close(ch)
    println(<-ch)
    println(<-ch)
    << 0
}

预期 xu check：通过。 xu run 输出（逐行）：7 / 0.

@main

fn bad() {
    close(1)
}

预期 xu check --lib：失败，诊断包含 close requires a channel, found int.

向已关闭信道发送是运行时错误，并非静态所有权错误。此函数能通过检查；本机测试入口调用它时退出码为 1。浏览器解释器报告 send on closed channel。因此它有意不提供运行按钮。

@main

fn wrong() {
    ch := chan int{cap: 1}
    close(ch)
    ch <- 1
}

预期 xu check --lib：通过。

Select：等待就绪，或进行非阻塞探测

每个分支由发送或接收操作及其分支体构成。没有 else 时，select 等待某个操作就绪；带 else 时，若没有就绪操作，立即进入该分支：这是非阻塞就绪探测，不是超时。已关闭的空信道可立即接收并产生零值。多个分支同时就绪时，不应依赖分支顺序或公平性。

@main

fn main() int {
    ch := chan int{cap: 1}
    select {
        ch <- 7 { println("sent") }
        else { println("full") }
    }
    select {
        value := <-ch { println(value) }
        else { println("empty") }
    }
    select {
        value := <-ch { println(value) }
        else { println("empty") }
    }
    << 0
}

预期 xu check：通过。 xu run 输出（逐行）：sent / 7 / empty.

Select 至少要有一个通信分支；只有 else 是无效的。

@main

fn bad() {
    select {
        else { println("idle") }
    }
}

预期 xu check --lib：失败，诊断包含 select requires at least one send/recv case.

取消与阻塞是两件事

仅限本机 SDK。 取消需要任务协作观察信号。下例由调用方关闭专用 stop 信道；等待工作任务时，工作协程仍能观察停止信号，因为两个操作在同一个 select 中。独立的确认信道让调用方等待工作协程结束。示例没有发送工作任务，因此只有 stop 分支就绪。

@main

fn worker(jobs chan int, stop chan int, done chan int) {
    select {
        signal := <-stop { println("stopped") }
        job := <-jobs { println(job) }
    }
    done <- 1
}

fn main() int {
    jobs := chan int{cap: 0}
    stop := chan int{cap: 0}
    done := chan int{cap: 0}
    xu worker(jobs, stop, done)
    close(stop)
    println(<-done)
    << 0
}

预期 xu check：通过。 xu run 输出（逐行）：stopped / 1.

关闭 stop 不会强制中断另一个信道上的接收，也不会中断无关的阻塞 OS / FFI 调用。应把取消与正在等待的操作放进同一个 select，或使用该 API 明确提供的取消机制。取消退出与其他退出路径一样，须释放 owned 资源并显式 dispose 原生句柄。工作与取消同时就绪时，须允许工作分支胜出；取消没有优先保证。

检查通过不代表一定能推进。下列函数没有发送方或关闭方，单独执行时接收无法完成；仅作为库片段检查，不执行。

@main

fn wait_without_sender() int {
    ch := chan int{cap: 0}
    << <-ch
}

预期 xu check --lib：通过。

在循环里反复进入 else 不会等待工作。若本意是等待，优先使用带 stop 分支的阻塞 select。纯 CPU 工作与阻塞宿主调用也需要明确设计推进与取消方式；xu 不是能把任何操作变成非阻塞的包装。

原生与浏览器 WASM 的边界

关注点原生 SDK本站浏览器 Playground
执行方式自研 AOT 后端；宿主运行时有 OS 工作线程，可并行运行协程。WASM 中的 MIR 解释器；在浏览器 worker 中协作调度任务，Xu 任务之间没有 CPU 并行。
信道等待挂起等待协程，在通信或关闭时唤醒。让出给其他解释执行的任务；所有任务均阻塞时产生信道死锁诊断，执行还受步数限制。
宿主操作OS、网络、原生 / FFI API 取决于包与目标支持；OS 调用可能阻塞一个工作线程。浏览器沙箱与 canvas UI 子集；原生文件、socket、C FFI 与桌面 UI 不在此运行时范围内。
示例验证范围Linux x64 上的检查与所列输出；没有性能或调度顺序保证。简单发送 / 接收、close 与非阻塞 select 示例也已在此运行；不能据此推断任意 WASM 宿主的能力。

已确认的浏览器限制： 取消示例中的多分支阻塞 select 在此解释器中报告 unsupported playground builtin: 151，因此该程序仅限本机；上面的带 else 非阻塞 select 可在浏览器运行。原生 I/O 取消另须考虑具体 API 与目标支持。

待验： 跨平台原生运行、CPU 并行吞吐量、真实原生 I/O 的取消不在这些示例的验证范围内。原生 API 辅助片段标为仅限本机。沙箱限制见演练场；生命周期与 dispose 规则见内存模型。
