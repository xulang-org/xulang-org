官方扩展包 (Packages)

官方模块：github.com/xulang-org/packages · SDK 内模块版本 1.0.2 · 29 个服务集成包及共享 transport 包

Xu {{xu_version}} SDK 内置 1.0.2 版驱动和原生源码资源。下文介绍的 AI 与 GPU 扩展包来自独立的 1.17.0 版源码。选用依赖时请核对各 API 页面标注的源码版本。

1. 选择 SDK 内置包或固定源码提交

将项目放在解压后的 SDK 旁，通过本地来源声明内置 packages；安装位置不同时调整相对路径：

module: my_app
version: !ver 0.1.0
xu: !ver {{xu_version}}
require:
  "github.com/xulang-org/packages": file:../xu-v{{xu_version}}/packages

也可以指定该 SDK 使用的完整不可变提交来获取源码：

require:
  "github.com/xulang-org/packages": git:https://github.com/xulang-org/packages.git@c16af7ca38dc31c289ca83670edf153f1f85f5f2

在项目目录中解析并锁定依赖，再检查和构建：

xu install
xu check main.xu --offline
xu build main.xu -o my_app

模块版本与 Git 标签分别管理：本安装包声明模块版本 1.0.2，以上固定源码地址直接选择准确提交。请将 xu.lock 与应用一同维护；冻结构建、vendor 和代理用法见模块与依赖。

2. 在代码中引用扩展包

Xu 对所有外部扩展包采用明确的命名空间别名机制，语法格式为：别名 #完整包路径。这不仅避免了全局命名污染，也保证了所有代码依赖关系透明可见。

@main

// 1. 标准库无需别名，以 # 开头
#database/sql

// 2. 外部 packages 扩展包声明别名与完整路径（别名即代码中的调用命名空间）
mysql    #github.com/xulang-org/packages/mysql
redis    #github.com/xulang-org/packages/redis
postgres #github.com/xulang-org/packages/postgres

fn main() int {
    // 直接通过别名访问包内公开接口
    println("Drivers loaded successfully")
    << 0
}

注意：请勿写成 #mysql 或 #redis。外部扩展必须声明别名和完整模块路径；标准库导入与本地包导入（例如 #util）遵循各自解析规则。本页列出的集成属于 github.com/xulang-org/packages，其他外部模块按各自模块身份声明。

3. 快速上手代码示例

示例 1：通过标准库 database/sql 使用 MySQL 驱动

标准库 database/sql 提供连接池、事务与结果行读取抽象，底层具体数据库驱动由 packages/mysql 实现：

@main
#database/sql
mysql #github.com/xulang-org/packages/mysql

fn main() int {
    dsn := "root:123456@tcp(127.0.0.1:3306)/test_db?tls=false"
    $db := sql.open(mysql.driver(), dsn)
    db.ping() >>> (err) {
        println("数据库连接探测失败: " + err.msg())
        << 1
    }
    println("MySQL 连接成功！")
    db.close() >>> (err) { << 1 }
    << 0
}

@main

fn main() int {

5. 边界与注意事项

  • SQLite 与多后端 GPU 纯 FFI / dlopen 架构：SQLite 驱动通过纯 Xu 包 sqlite_native 动态加载（dlopen）系统 libsqlite3（Windows 自动识别系统 winsqlite3.dll，支持 XU_SQLITE_LIBRARY 覆盖），无需编译 .xulib。CUDA 与 Vulkan 同样采用纯 Xu dlopen（cuda_native / vulkan_native）；Metal GPU 包通过 metal_native 动态加载 libxu_metal.dylib（支持 XU_METAL_LIBRARY 覆盖）。
  • 离线与生产构建（Frozen Builds）：在生产 CI/CD 流水线中，提交生成的 vendor/ 和 xu.lock 并运行 xu build main.xu --frozen，严格禁止构建期间发起网络请求。

AI 包与驱动已知边界与局限

上线前必读：以下边界条件结合 Xu v0.14.3 与 packages v1.17.0 源码事实总结，接入生产前请按需配置外部存储或代理：

  • 多后端 GPU 的硬件与环境前提：metal 与 llm_metal 仅在 Apple Silicon macOS 上可用（使用前需构建 libxu_metal.dylib 或通过 XU_METAL_LIBRARY 指定路径）；cuda_native 依赖宿主机 NVIDIA 驱动/NVRTC/cuBLAS 动态库；vulkan_native 依赖 Vulkan 1.1 运行时。llm_engine 主程序仍为 CPU 多线程（--threads N），不直接调度 llm_metal/CUDA。
  • 签名与 SQLite 驱动简化：自 Xu v0.14.3 起编译器已在构建阶段直接嵌入 Mach-O LC_CODE_SIGNATURE 签名，无需再手工执行 codesign；SQLite 通过纯 Xu sqlite_native 动态加载，不再需要编译 .xulib。
  • 向量存储与高并发网关选型：PgVectorPool 现已提供基于 #database/sql 连接池的多连接并发能力（原 PgVectorClient 仍保持单连接向后兼容）；rag.SqliteVectorStore虽新增内存缓存与刷新增量，但检索仍为 $O(N)$ 全量余弦/BM25 扫描（适合万级以内切片），更大规模请选用 PgVectorPool（HNSW/IVFFlat）或 QdrantVectorStore。
  • 网关、协议与护栏注意项：gateway 现支持通过 Redis 共享熔断/限流/费用与缓存状态，但 SSE 流式故障转移仍只发生在首个流块到达前，跨厂商映射覆盖公共字段而非各厂商私有扩展；a2a 已支持 API Key / 自定义鉴权钩子与 SQLite 持久化，生产暴露公网时仍建议前置反向代理/TLS；高风险安全审查建议组合使用 guardrails.strict_policy 与 check_safety_openai。
