什么是 Xu 编程语言？

Xu 是一门静态类型系统编程语言，采用自研原生与 WebAssembly AOT 后端。它结合所有权推断、借用检查与确定性资源释放，无需垃圾回收器，并内建协程（xu f()）与类型安全通道（chan T）。它既可用于构建高并发网络服务与跨平台原生桌面 UI，也原生支持无宿主裸机固件与操作系统微内核开发。

Xu 相比 Rust 与 Go 有哪些区别？

Xu 推断所有权并确定性释放资源，无需显式生命周期标注（如 <'a>）。它提供类似 Go 的协程与类型安全通道，以所有权和借用检查替代垃圾回收器。在底层与内核开发方面，Go 强绑定 GC 与庞大运行时而无法直接编写裸机微内核；Rust 虽支持 no_std，但在复杂系统开发中常面临繁琐的生命周期标注；Xu 则通过 profile: freestanding 无宿主模式与纯静态 #core 库提供零 GC 原生开发体验，同时保持免生命周期标注的人性化语法，将底层硬件操纵严格限制在 unsafe 隔离边界内。安全限制见内存安全说明；运行时间与内存的实测结果见基准看板。

Xu 语言是否有垃圾回收（GC）？

没有。Xu 通过所有权推断与 RAII 在作用域退出时确定性释放资源，不依赖运行时垃圾回收器。所有权检查及 &T 共享借用 / $&T 独占借用检查，可防止受检查 Xu 代码中的一类生命周期与别名访问错误。

并发代码中的共享可变状态仍需适当同步。原生代码、FFI 与并发库各有安全要求；这些检查不保证所有程序都没有数据竞争、泄漏或未定义行为。分配、调度与 I/O 仍可能造成延迟波动。详见所有权与借用、并发和原生模块边界。

Xu 编译器是否使用了 LLVM？为什么采用自研后端？

没有使用 LLVM。Xu 编译器采用自研 MIR（中间表示）、寄存器分配器及面向 Mach-O、ELF、PE 与 WebAssembly 的代码发射器。原生模块与桌面构建可能需要宿主库及匹配的 C 工具链；详见原生模块与桌面构建要求。

Xu 如何支持操作系统内核与裸机固件开发？

原生支持从零编写操作系统微内核、裸机固件与硬件驱动程序。不同于依赖运行时垃圾回收（GC）的托管语言，也不同于需要复杂显式生命周期标注的语言，Xu 采用严格分层的底层系统架构：

  • 在普通系统组件与内核服务逻辑中，严格保留隐式所有权推断与编译期确定性析构，无需垃圾回收器也无须手写 <'a> 生命周期标注；
  • 在最底层的硬件交互（约占 5% 代码）中，通过无宿主模式（freestanding）、裸指针（*raw T）、易失访存屏障（volatile_read / volatile_write）与纯静态核心库（#core）进行精确受控的微架构操纵。

操作系统研发指南提供内核示例的构建步骤与硬件 API 入口。Xu 0.14.0 发布公告记录了裸机工具链的发布内容。

什么是无宿主模式（Freestanding Profile）？如何彻底阻断外部 OS 依赖？

无宿主模式指编译产物完全不依赖外部操作系统内核的系统调用（Syscalls）、动态链接器以及 C 运行时库（libc）。Xu 提供三级声明机制：

  • 源码级标记：源文件首行声明 $freestanding 编译标签；
  • 工程级清单：在项目配置文件 xu.xun 中声明 profile: freestanding；
  • 命令行参数：编译时传入 --profile=freestanding 或 --no-std。

开启该模式后，编译器将彻底剥离宿主 OS 运行时、默认协程调度器与标准 I/O 运行时，直接输出纯净独立的裸机 ELF / PE 镜像，产物尺寸通常仅 1.9 KB ~ 2.4 KB。

在没有标准库的裸机环境下，Xu 提供哪些核心硬件抽象与并发原语？

Xu 交付了纯静态、零系统调用、零隐式分配的核心基础库 #core，包含现代内核研发的必备模块：

  • #core/arch：CPU 特权指令（cli、sti、hlt、pause、wfi）、控制寄存器访问（CR0/CR2/CR3/CR4、VBAR、SCTLR）、8259A PIC 中断芯片重映射、8254 PIT 可编程定时器初始化及 IDT 中断门描述符加载（load_idt）；
  • #core/sync：提供中断安全自旋锁 IrqSpinlock 与普通自旋锁 Spinlock，配合 RAII 守卫（IrqGuard、SpinGuard）实现作用域退出时确定性解锁并自动恢复 CPU 中断标志位（EFLAGS / PSTATE），即使在内核中断上下文也保证零泄漏与无锁死；
  • #core/task：跨架构 192 字节 16 字节对齐的微任务上下文结构 TaskContext、原子级硬件上下文切换（switch_context）、TrapFrame 异常现场快照与系统调用分发入口；
  • #core/virtio：纯静态 VirtIO MMIO 驱动框架、VirtQueue 描述符环、VirtioBlkDriver 磁盘块设备与 VirtioNetDriver 虚拟网卡驱动；
  • #core/mem 与 #core/alloc：零依赖内存原语（memset/memcpy/memcmp）与可插拔全局分配器契约 GlobalAlloc，可直接接入伙伴系统（Buddy System）或 Slab 分配器。

内核中如何安全地进行物理内存映射（MMIO）与裸指针操作？

硬件寄存器与外设内存访问要求精确受控的语法屏障：

  • 裸指针类型 *raw T 与 unsafe { ... } 块：允许进行绝对物理地址重解释与指针算术，但解引用必须强制包裹在 unsafe { ... } 隔离块中。所有权推断跳过裸指针，确保底层危险操作不污染上层内核业务逻辑；
  • 易失访存屏障（Volatile MMIO）：提供内置 volatile_read 与 volatile_write 原语，防止编译器优化通道将其作为死代码消除（DCE）或进行循环不变量外提（LICM）；
  • 精确内存布局控制：支持 @repr("C", align: N)（如 4KB 页面对齐 @repr("C", align: 4096) 用于 PML4 页表）和 @repr("C", packed) 紧凑排布（用于硬件协议帧与描述符）；
  • 脚手架与仿真集成：使用 xu init --baremetal my_os 一键生成多架构内核工程、链接脚本（linker.ld）与 Makefile，并通过 make qemu 即可在 QEMU 模拟器中直接引导运行。

Xu 支持原生桌面 UI 吗？必须使用 WebView 吗？

支持，而且 WebView 是可选项。当前 Xu {{xu_version}} 正式 SDK 提供两种界面方式：使用 #ui/draw、#ui/layout 和 #ui/widgets 编写原生绘图与控件界面；或使用 #ui/webview 承载 HTML/CSS/JavaScript，通过请求桥接与 Xu 交互。原生控件示例不需要 HTML、CSS 或 JavaScript。

桌面 UI 支持哪些平台？需要安装什么？

桌面宿主覆盖 macOS、Windows 和 Linux。macOS 使用 AppKit，网页使用 WebKit；Windows 使用原生宿主，网页需要 WebView2；Linux 使用 GTK4，网页另需 WebKitGTK 6.0。构建与打包需要对应平台的宿主工具链；原生绘图与控件不要求应用嵌入 WebView。

原生 UI 目前有哪些能力边界？

现有组件覆盖常用桌面交互，仍有明确边界：Input / TextArea 是纯文本编辑器；Table 为有界数据表，排序与取数由应用处理；列表与树不提供按需构建的无界数据虚拟化。富文本、高级表格、拖拽工作区与完整辅助技术桥接仍需进一步开发。

xu get 与 xu install 有什么区别？

在已有 xu.xun 的项目根目录执行 xu get <module>@<version>，即可添加或更新指定依赖：自动修改清单中的 require:、安装源码到 vendor/ 并更新 xu.lock。请将占位符替换为真实模块与已确认发布的 SemVer 标签，不接受 @latest。官方扩展包请使用 SDK 内置包或匹配的固定源码提交，再运行 xu install。

xu install 则安装清单中已经声明的依赖。两者均支持 --offline；需要严格按现有锁文件构建时，使用 xu build . --frozen。详见模块与依赖；官方 packages 仓库提供 29 个扩展包。

如何用 xu native 集成 C 代码？

xu native 提供完整的原生模块流程：xu native compile 将 C 源码与接口元数据编译为 .a；xu native archive 为已有目标文件封装元数据；xu native pack 将不同目标的切片打包为 .xulib；xu native inspect 与 xu native extract 用于检查和提取切片。

什么是 XACP？

XACP（Xu Agent Control Protocol）是用 xu build --xacp 和/或 --xacp-port PORT 构建的 hosted native 程序的帧控制通道。该构建会嵌入发现信息。./app --xacp-help 打印机器可读摘要，其中 capabilities 为 stdio，并标明 TCP 是否启用以及绑定地址。这取代了早先只含 help-only 的发现文本。

#xacp（src/xacp）是与传输无关的安全核心：帧与 XUN 校验、权限、会话生命周期。单独导入 #xacp 不会装上启动期控制入口。stdio 与本机回环 TCP 是 --xacp 构建插入的运行时钩子。启动器是 xu xacp，它转而执行伴生工具 xu-xacp。模式为 inspect、run、debug、record、control、attach、connect。API 已包含在正式 {{xu_version}} SDK 提取结果中，契约依据对应发布源码。原生会话和平台/UI 运行验收仍待验。见命令行参考、#xacp API与对应发布源码。

XACP 的 stdio 与本机回环 TCP 有什么区别？

stdio。用 --xacp-stdio 启动目标，或执行 xu xacp control <program>。会话独占 stdin 与 stdout。帧使用 XACP/1\n<N>\n，后接恰好 N 个 UTF-8 字节的纯 XUN 正文。正文换行计入，前缀不计入；没有结束分隔符。传输层去掉前缀后才调用 parse_frame，见精确字节示例。业务 main 不会运行。

本机回环 TCP。用 --xacp-port N 构建，N 为 1..65535，然后运行 <app> --xacp-tcp。进程只监听 127.0.0.1:N。另一个终端执行 xu xacp connect PORT，逐帧中继同样的请求与响应。端口 0 关闭 TCP（发现信息为 tcp: disabled (port 0)），stdio 能力仍然保留。每个已接受的连接是独立会话。连接按顺序处理；失败的对端只结束自己的会话，监听继续。stdio 会话结束时进程退出。-- 之前的第一个控制标志优先。普通启动不监听，也不读取控制 stdin。

xacp.hello 会授予什么权限？

控制会话开始时没有权限，首个请求必须是 xacp.hello，携带 id: !i 1、ver: !ver 1.0.0 和非空 nonce。宿主未设置非空 XU_XACP_TOKEN 时，允许的权限仅为 PERM_INFO（1），即使客户端提供 token 或宿主设置了 XU_XACP_ALLOW_RAW=1 也不例外。配置非空 token 后，hello 必须通过 token 提供它，并由 crypto/subtle.constant_time_compare 做常数时间比较；缺失、为空或不匹配均返回 auth_failed 并关闭会话。匹配时默认允许掩码 15，只有宿主精确设置 XU_XACP_ALLOW_RAW=1 才允许 31。可选的 permissions: !i 0..31 用于请求权限，实际授予 requested & allowed；省略时请求整个允许掩码。

development 权限是显式宿主策略，stdio 与 TCP 传输不会自动开启；进入 OPEN 后权限不可再更改，schema、帧大小、窗口与生命周期检查仍然适用。默认启用的 nonce 重放检查在认证和权限校验后执行；检测到重放时返回同一请求 id 的 nonce_replay，清除会话并断开，不进入 OPEN。成功帧含整数 id: !i 和 ok: !b true，其 data 含 state: OPEN、经路径过滤并加引号的 nonce、实际授予的整数 permissions: !i 与 permission_label：掩码 0 为 none，1 为 info，31 为 development，其余为 custom。proc.output 是否可用取决于宿主的输出捕获支持，不依赖 Screen；独占启动适配器没有注册 Screen，授权后的 UI 操作返回 not_implemented，应用调用 attach API 后注册并持续 poll Screen，UI 操作便可经 Screen marshal 处理，能力边界见下文。

xu xacp control 与 xu xacp run 有什么区别？

xu xacp run <program> -- args... 会启动程序，业务 main 会运行。工具会再插入一个 --，因此名为 --xacp-help 的业务参数不会触发发现。debug 先打印 --xacp-help，再按同样方式运行。它不是断点调试器。record 在 Unix 上流式输出最多 1 MiB 的 stdout，stderr 仍留给终端。该输出不是 XACP UI 录制，Windows 上的 record 仍不可用。inspect 执行 --xacp-help，不接受业务参数，但同样会运行目标程序。

control 启动 --xacp-stdio，继承调用方的 stdin 与 stdout，跳过业务 main，并且不接受业务参数。connect PORT 不接收程序路径，只把帧中继到 127.0.0.1:PORT。run、debug、record 的用户参数必须写在工具自己的 -- 之后。

XACP 目前有哪些安全限制？

启动器只应指向受信任的本地可执行程序。inspect 也会执行它。没有 TLS，也不能绑定 127.0.0.1 以外的地址。生成器只允许 hosted native 可执行程序：库、共享对象、测试脚手架、嵌入式目标和 --desktop 都会被拒绝。未设置非空 XU_XACP_TOKEN 时仅允许 INFO 只读访问；需要控制能力时须设置 XU_XACP_TOKEN。

独占启动适配器（--xacp-stdio、--xacp-tcp 或 xu xacp control）跳过业务 main，没有注册 Screen，授权后的 UI 操作返回 not_implemented。库函数 xacp.attach_stdio() / xacp.attach_tcp(port) 让应用 main 运行，由应用注册 Screen 并持续调用 xacp.poll；ui.tree、ui.screenshot、ui.input、ui.act、ui.record 经 Screen marshal 访问真实界面。Screen 关闭或注销后，等待中的请求返回 stale_window，后续 UI 请求返回 not_implemented。xu xacp attach <program> -- args... 以安全的 -- 参数边界启动应用，应用代码仍需调用 attach API。

按 dev 协议，已注册 Screen 时，ui.record 在单次请求内完成有界 XAR1 采样，返回 mode、records、bytes、truncated 和 payload。请求需提供正数 win 与 mode: events|frames，可选 max_bytes、max_records、duration_ms。客户端重复请求拉取后续片段；每次请求只有一个响应，不保留跨请求录制状态或续传游标。stream_required 仅保留给无 sink/采样能力的适配器，内置 Screen 采样路径不返回它。

events 目前是带 state=true 的当前 window/canvas/generation/open 状态观测，没有真实输入事件日志；采样不注入输入，也不推进应用事件循环。frames 仅返回尺寸且 redacted=true，不含像素。CLI xu xacp record 录制的是 stdout，与 ui.record 的 UI 采样不同。参数边界、截断和错误语义见 API 录制说明。

proc.output 在启用 --xacp 插桩的 64 位 POSIX 生成宿主上捕获 Xu 运行时 print / eprint 与运行时 fd-write 路径的 fd 1/2 写入，不捕获外部原生代码或子进程的写入。Windows 与未插桩构建返回 not_implemented；仅调用 attach API 不会增加输出捕获能力。

XU_XACP_WRITE_TIMEOUT_MS 默认 10000 ms，范围 1..600000；按每个完整出站帧计时，部分写入进度不续期。超时视为传输失败，不再发送帧并关闭会话：独占 stdio 非零退出，TCP 只断开该对端并继续监听；stderr 打印 xacp: write timed out after W ms，W 为配置值。Windows 管道或控制台 stdio 的写超时仅尽力生效，阻塞写入仍可能无界等待。

写超时与读侧 XU_XACP_HELLO_TIMEOUT_MS（默认 5000 ms）、XU_XACP_IDLE_TIMEOUT_MS（默认 60000 ms，0 关闭）及 attach UI 等待的 XU_XACP_REQUEST_TIMEOUT_MS（默认 5000 ms）相互独立。xu xacp connect 自身没有应用级响应截止，整体进程超时仍由调用方负责。完整契约见#xacp API与XACP 协议规格。

Xu 如何在不依赖 C/C++ 运行库的情况下运行本地大模型推理？

examples/llm_engine/main.xu 是纯 Xu 编写的独立推理引擎，原生支持混合量化 GGUF（Q4_K_M 含 Q4_K/Q6_K，以及 F32、F16、BF16、FP8 E4M3、Q4_0、Q8_0）与 Safetensors、Qwen3/Gemma2 逐头 qk_norm、ChatML 自动模板、基于 #tensor 的紧凑权重与分页 KV 缓存（--kv-dtype f16|bf16|fp8_e4m3fn）、UTF-8 BPE 分词合并、可重复采样控制（--top-p、--repeat-penalty、--seed）、突破 2048 限制的大隐藏维度支持，以及具备多槽连续批处理与 Prefix KV 缓存复用的 OpenAI 兼容 serve 服务模式（/health、/v1/completions、/v1/chat/completions 支持 SSE stream: true 与 stop，以及 /v1/embeddings）。详见AI 推理运行指南。

#tensor 与编译器 MIR 张量融合如何加速数值与模型计算？

标准库 #tensor 提供 IEEE/FP8 低精度标量转换、紧凑跨步视图、GGML Q4Block/Q8Block/Q4KBlock/Q6KBlock 块解码（含零分配 dot_f32）以及 20 个纯 Xu 向量/矩阵算子（dot_f32、axpy_f32、vadd_f32、vsub_f32、vmul_f32、vscale_f32、silu_f32、gelu_f32、rmsnorm_f32、layernorm_f32、l2_normalize_f32、cosine_similarity_f32、softmax_f32、swiglu_f32、rope_f32、matvec_f32、matmul_f32、argmax_f32、quantize_q8_0、quantize_q4_0_row）。在 XU_TENSOR_FUSION=1 编译模式下，MIR 降级通道会自动识别这些纯 Xu 循环并下沉为原生 ARM64 NEON/SDOT 与 x86-64 SSE2/AVX2 内核，包括 __xu_tensor_vmul_f32 与 head_dim=128 分页注意力加速。详见编译器张量融合。

Xu 是否支持 GPU 加速用于 AI 计算？

支持。在 macOS 上，官方外部包 github.com/xulang-org/packages/metal（v1.3.0）提供 F32Matrix、F16Matrix（MPSDataTypeFloat16）与原始 GGML Q4Matrix（matrix_q4_0）存储、并发读锁隔离、单命令缓冲区多算子 Batch 编排（d.begin_batch() / b.commit()）、MPS 矩阵乘法（gemm_f32/gemm_f16 及 _nt 转置版本）、融合寄存器反量化 gemv_q4_0_f32 以及覆盖完整 Transformer 层的 Metal 着色器算子（rmsnorm_f32、layernorm_f32、softmax_f32、gelu_f32、swiglu_f32、add_f32、mul_f32、scale_f32、rope_f32 与 causal_attention_f32）。详见Metal GPU 计算与外部包文档。

Xu 的 AI 生态包含哪些向量数据库与智能体协议支持？

官方 packages 仓库提供纯 Xu 实现的 Qdrant、Milvus 和 Chroma 向量数据库客户端，与 #tensor 和 metal GPU 共同构成完整检索与推理底座；同时编译器内置 XACP 协议，让 AI 智能体可直接对本地桌面应用进行结构化观测与自动化操作。详见AI 生态组件。
