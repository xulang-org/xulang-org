常见问题解答 (FAQ)

关于 Xu 语言设计、内存模型、编译架构、桌面 UI、编辑器支持、依赖管理、原生互操作与 XACP 的核心问答

什么是 Xu 编程语言？

Xu 是一门现代静态强类型、超音速 AOT 编译的原生系统级编程语言，专为高并发云原生后端、网络基建与低延迟系统软件而设计。它在无需垃圾回收（零 GC）的前提下，通过编译期确定性 RAII 所有权、轻量级原生协程（xu f()）与类型安全通道（chan T）实现卓越的内存安全与并发吞吐。

Xu 编译器是否使用了 LLVM？为什么采用自研后端？

没有使用 LLVM。Xu 编译器采用完全自主研发的轻量 MIR（中间表示）、寄存器分配器与直接原生机器码发射器，直出 Mach-O、ELF、PE 与 WASM 二进制。LLVM pass 链庞大沉重，是 C++/Rust 编译速度慢的根源；Xu 追求类似 Go 的亚秒级极致编译速度，且编译器本身为单文件极简二进制，零外置 C++ 动态库依赖，真正开箱即用。

Xu 语言是否有垃圾回收（GC）？

没有。Xu 完全不依赖任何运行时垃圾回收器（Zero GC），没有 Stop-The-World (STW) 暂停。内存由编译期唯一所有权跟踪与 RAII 作用域析构确定性释放，并通过 &T 共享借用与 &mut T 独占借用在编译阶段彻底消除悬垂指针、内存泄漏与多线程数据竞争。

Xu 相比 Rust 与 Go 有哪些区别？

相比 Rust，Xu 在提供同等确定性零成本内存安全的同时，去除了复杂的显式生命周期标注（如 <'a>），并将轻量协程与通信通道作为语言一等公民内置，无需引入笨重的外部异步运行时；相比 Go，Xu 保持了轻快直观的并发体验，但编译为零 GC 原生机器码，完全没有并发三色标记清除 GC 的内存常驻底线与停顿延迟。

Xu 的编译速度与实际执行性能如何？

可复现的性能实测：47 项负载覆盖 ARM64、x86-64 六个平台，对照 Xu、C、Rust、Go 和 Swift。横测看板展示各平台的运行耗时、CPU 时间、峰值内存与二进制体积；C、Rust 按负载选取同平台 O1–O3 的最小实测中位数。编译耗时记录在来源 CI 的原始报告中。

Xu 是否原生支持 WebAssembly (WASM)？

原生一等公民支持。编译器内建 wasm32 直接后端（xu build --target wasm32），无需 Emscripten 或外置工具。官网上的在线演练场（Playground）正是将 Xu 编译器源码直接编译为 WASM，纯浏览器前端运行，免安装即可体验实时语法编译与借用检查。

Xu 支持原生桌面 UI 吗？必须使用 WebView 吗？

支持，而且 WebView 是可选项。当前 Xu {{xu_version}} 正式 SDK 提供两种界面方式：使用 #ui/draw、#ui/layout 和 #ui/widgets 编写原生绘图与控件界面；或使用 #ui/webview 承载 HTML/CSS/JavaScript，通过请求桥接与 Xu 交互。原生控件示例不需要 HTML、CSS 或 JavaScript。

#ui 提供窗口、事件、菜单、托盘、多窗口、剪贴板和文件对话框等桌面服务。控件由 Xu 在原生 Canvas 上绘制，系统菜单与对话框使用宿主外观。入口见UI / WebView 开发指南和控件 API 与示例。

UI 有哪些控件？支持中文输入和主题吗？

SDK 包含按钮、勾选框、开关、单选、滑块、步进器、标签页、列表与选择器；Input / TextArea 支持原生文字输入会话、IME、选区及复制粘贴。还提供 Table、TreeView、Pagination、ComboBox、MultiSelect、DatePicker、TimePicker、ColorPicker，以及 Popover、Tooltip、Toast、Modal 等组件。

控件共享深色、浅色和高对比度主题，支持字体与文字缩放、密度、状态样式和局部覆盖。保留布局与 Screen 上下文可协助组织控件、焦点、事件和重绘。绘图、编辑与主题的用法见样式指南和可运行示例。

桌面 UI 支持哪些平台？需要安装什么？

桌面宿主覆盖 macOS、Windows 和 Linux。macOS 使用 AppKit，网页使用 WebKit；Windows 使用原生宿主，网页需要 WebView2；Linux 使用 GTK4，网页另需 WebKitGTK 6.0。构建与打包需要对应平台的宿主工具链；原生绘图与控件不要求应用嵌入 WebView。

先运行 xu doctor --desktop 检查依赖，使用 WebView 时再加 --webview。应用目录包含 xu.xun、main.xu 与应用图标，使用 xu build <AppDir> --desktop 打包；完整命令见构建指南。编译器支持某个目标不等于桌面 UI 已在该目标完成运行验收；浏览器 WASM 演练场不运行桌面 UI。范围见限制与现状。

原生 UI 目前有哪些能力边界？

现有组件覆盖常用桌面交互，仍有明确边界：Input / TextArea 是纯文本编辑器；Table 为有界数据表，排序与取数由应用处理；列表与树不提供按需构建的无界数据虚拟化。富文本、高级表格、拖拽工作区与完整辅助技术桥接仍需进一步开发。

平台文字排版、IME 与系统服务也需要在真实目标系统上验收，不能以跨平台编译通过代替交互验证。选用组件前请查看对应 API 契约和示例说明。

Xu 支持哪些编辑器？如何启用 LSP？

官方 vscode-xu 扩展支持 VS Code 与 Cursor，通过 xu lsp 启动 SDK 中的 xu-lsp 语言服务器，提供实时诊断、代码补全、跳转定义、悬停文档、符号大纲、查找引用、重命名与格式化。

其他支持 LSP 的编辑器也可配置 xu lsp 作为服务器命令，通过标准输入输出（stdin/stdout）交换 JSON-RPC 2.0 消息。通常由编辑器自动启动；可用 xu lsp --help 查看帮助。

xu get 与 xu install 有什么区别？

在已有 xu.xun 的项目根目录执行 xu get <module>@<version>，即可添加或更新指定依赖：自动修改清单中的 require:、安装源码到 vendor/ 并更新 xu.lock。请将占位符替换为真实模块与已确认发布的 SemVer 标签，不接受 @latest。官方扩展包请使用 SDK 内置包或匹配的固定源码提交，再运行 xu install。

xu install 则安装清单中已经声明的依赖。两者均支持 --offline；需要严格按现有锁文件构建时，使用 xu build . --frozen。详见模块与依赖；官方 packages 仓库提供 29 个扩展包。

如何用 xu native 集成 C 代码？

xu native 提供完整的原生模块流程：xu native compile 将 C 源码与接口元数据编译为 .a；xu native archive 为已有目标文件封装元数据；xu native pack 将不同目标的切片打包为 .xulib；xu native inspect 与 xu native extract 用于检查和提取切片。

.a 用于单目标静态库，.xulib 用于携带接口契约与多个目标切片的分发。在 macos-arm64 或 macos-x64 上，构建时可直接传入库，例如 xu build main.xu native/mylib.xulib -o app。其他目标须输出并转换 XUOBJ，再外部链接。编译 C 源码需安装相应的 C 编译工具链。参数与完整示例见原生模块与 .xulib 规范，或运行 xu native compile --help。

Xu 目前支持哪些操作系统与 CPU 芯片架构？

原生支持主流跨端全矩阵：操作系统覆盖 macOS、Linux、Windows (PE AOT) 及 WebAssembly；CPU 架构支持 ARM64 (Apple Silicon / AWS Graviton)、x86-64 (Intel / AMD)、LoongArch64 (龙芯)、RISC-V 64/32 及 Linux ARM32。

什么是 XACP？

XACP（Xu Agent Control Protocol）是用 xu build --xacp 和/或 --xacp-port PORT 构建的 hosted native 程序的帧控制通道。该构建会嵌入发现信息。./app --xacp-help 打印机器可读摘要，其中 capabilities 为 stdio，并标明 TCP 是否启用以及绑定地址。这取代了早先只含 help-only 的发现文本。

#xacp（src/xacp）是与传输无关的安全核心：帧与 XUN 校验、权限、会话生命周期。单独导入 #xacp 不会装上启动期控制入口。stdio 与本机回环 TCP 是 --xacp 构建插入的运行时钩子。启动器是 xu xacp，它转而执行伴生工具 xu-xacp（模块 0.1.1）。模式为 inspect、run、debug、record、control、connect。该行为来自语言仓库 0.10.10-dev.1（xu#23），不属于已发布的 {{xu_version}} SDK 提取结果。见命令行参考、#xacp API与可运行样例。

XACP 的 stdio 与本机回环 TCP 有什么区别？

stdio。用 --xacp-stdio 启动目标，或执行 xu xacp control <program>。会话独占 stdin 与 stdout。帧为 --- !xacp … === 再加换行。业务 main 不会运行。

本机回环 TCP。用 --xacp-port N 构建，N 为 1..65535，然后运行 <app> --xacp-tcp。进程只监听 127.0.0.1:N。另一个终端执行 xu xacp connect PORT，逐帧中继同样的请求与响应。端口 0 关闭 TCP（发现信息为 tcp: disabled (port 0)），stdio 能力仍然保留。每个已接受的连接是独立会话。连接按顺序处理；失败的对端只结束自己的会话，监听继续。stdio 会话结束时进程退出。-- 之前的第一个控制标志优先。普通启动不监听，也不读取控制 stdin。

xacp.hello 会授予什么权限？

控制会话开始时没有权限。启动适配器校验 xacp.hello（ver: !ver 1.0.0，单调 id），begin 该请求，然后在 finish_request 之前、会话仍为 STATE_NEW 时调用 enable_development()。这会授予 PERM_ALL。成功帧报告 state: OPEN 与 permissions: development。schema 校验、会话生命周期、原生资源释放和帧上限仍然有效。

库函数 dispatch() 只完成 hello，不授予 development 权限。hello 已经结束、状态变为 STATE_OPEN 之后，enable_development() 返回 false。可选的 token 字符串只做 schema 检查；启动适配器不把它当作访问口令。development 权限打开后，proc.status 返回真实 pid。proc.output 与 UI 操作（ui.tree、ui.screenshot、ui.input、ui.act、ui.record）会先校验，在没有 Screen 或输出适配器时返回 not_implemented。

xu xacp control 与 xu xacp run 有什么区别？

xu xacp run <program> -- args... 会启动程序，业务 main 会运行。工具会再插入一个 --，因此名为 --xacp-help 的业务参数不会触发发现。debug 先打印 --xacp-help，再按同样方式运行。它不是断点调试器。record 在 Unix 上流式输出最多 1 MiB 的 stdout，stderr 仍留给终端。该输出不是 XACP UI 录制，Windows 上的 record 仍不可用。inspect 执行 --xacp-help，不接受业务参数，但同样会运行目标程序。

control 启动 --xacp-stdio，继承调用方的 stdin 与 stdout，跳过业务 main，并且不接受业务参数。connect PORT 不接收程序路径，只把帧中继到 127.0.0.1:PORT。run、debug、record 的用户参数必须写在工具自己的 -- 之后。

XACP 目前有哪些安全限制？

启动器只应指向受信任的本地可执行程序。inspect 也会执行它。启动通道上合法的 hello 会授予 development 权限，控制模式会跳过业务 main。没有 TLS，也不能绑定 127.0.0.1 以外的地址。目标持续无输出或不退出时，宿主没有超时或强制终止，调用方需要自行设置进程超时。这条通道还没有接入 UI Screen 适配器，因此 tree、screenshot、input、act、record 与 proc.output 不会返回真实界面数据。生成器只允许 hosted native 可执行程序：库、共享对象、测试脚手架、嵌入式目标和 --desktop 都会被拒绝。
