原生模块与 .xulib 规范

Xu {{xu_version}} · 原生 C/C++ 互操作 · 多数据类型映射 · 通用 .a 与便携式 .xulib 多目标切片规范

在系统级软件工程中，与成熟的 C/C++ 原生代码库集成是极其关键的基础能力。Xu 语言提供了零抽象成本、强类型检查的原生互操作机制。很多开发者在初次接触时会产生疑问：“为什么 Xu 既支持标准通用 .a（静态归档库），又要引入便携式 .xulib？”

本文档深入解析 Xu 的原生互操作机制、通用静态库与 .xulib 的分工定位、支持的完整数据类型映射表以及端到端完整的 7 个开发动作。

1. 核心结论：通用 .a 与 .xulib 的关系

  • 标准通用 .a（Unix 静态归档库）原生支持且地位完全平等：你可以直接使用本地系统编译器（如 clang、gcc、msvc）编译出标准的 .a，并在命令行 xu build main.xu module.a 或 xu.xun 的 native: 中直接声明引用，底层最终由操作系统原生链接器（ld / clang / lld）静态链接。
  • .xulib 是面向跨平台生态分发的“多目标切片元数据包”：它并不是一种全新的专有机器码格式，其内部包裹的依然是各个目标平台标准的 .a 静态切片，额外附加了强类型签名契约（JSON Manifest）与 SHA-256 完整性哈希。
特性维度通用 .a 静态库便携式 .xulib 容器包
适用场景单目标平台开发、本地临时调试、私有定制 C 链接跨平台模块分发、开源生态扩展包（如 packages/sqlite）
架构支持单架构单目标（如仅 linux-x64 或仅 macos-arm64）多目标多架构统一打包（单个文件内嵌全平台切片）
跨平台切换需在配置文件或构建脚本中编写复杂的 OS/Arch 切换条件构建器自动按当前 --target 提取匹配切片，零配置透明跨平台
类型安全仅含裸符号表（Symbol Table），丢失函数参数与返回值类型内置 JSON Manifest 与 XUOBJ 契约，编译期完成强类型检查
完整性校验无内置防篡改机制每个架构切片均记录 SHA-256 校验和，解包即校验

3. .xulib 内部结构与二进制规范

.xulib 是自描述的二进制容器（版本规范 xulib-1）。容器采用紧凑的线性段式布局，由魔数签名、定长头部、契约清单、切片索引表与二进制切片负载五大部分组成：

偏移区间 (Offset) 字段名称 (Field) 类型与长度 规范定义与字段语义
0x00..0x06 (7 Bytes) 魔数标识 (Magic) char[7] 固定为 "XULIB\x01\x00"，用于快速识别合规的 .xulib 二进制容器并校验主版本。
0x07..0x08 (2 Bytes) 次版本号 (Version) u16 (小端序) 容器格式次版本号，当前规范固定为 1。
0x09..0x0A (2 Bytes) 标志位 (Flags) u16 (位掩码) 保留供未来容器扩展（如压缩、嵌入式签名），默认填 0。
0x0B..0x0E (4 Bytes) 清单长度 (Manifest Len) u32 (小端序) 紧随其后的 JSON 契约文本总字节数 $N$。
0x0F..0x0F+N ($N$ Bytes) 契约清单 (Manifest) UTF-8 紧凑文本 自描述元数据：包含 module（全局模块名）、abi（接口协议版本）、exports（函数签名）及 slices（各平台散列）。
0x0F+N 之后 (4 Bytes) 切片总数 (Slice Count) u32 (小端序) 记录索引表中连续排列的多架构目标切片数量。
连续索引项 切片索引表 (Index Table) 变长结构体连续数组 每个切片条目顺序包含：
• target_len (u16) + target_name（如 "macos-arm64"）
• kind_len (u8) + kind（"archive" 静态库或 "object" 单对象）
• file_offset (u64) + file_size (u64) 绝对偏移与尺寸
• sha256 (32 Bytes) 二进制散列防篡改校验码
负载数据区 多目标负载 (Payloads) 二进制切片字节流 各平台标准的 .a 静态归档库：
• macOS：Mach-O 机器码对象 + xu.o（含 __DATA,__xumeta）
• Linux：ELF 机器码对象 + xu.o（含 .xumeta）
• Windows：COFF 机器码对象 + xu.o（含 .xumeta）

完整的 .xulib 二进制容器物理布局结构图：

+-------------------------------------------------------------------------+
| 0x00..0x06 | Magic Header (7 Bytes): "XULIB\x01\x00"                     |
+------------+--------------------+---------------------------------------+
| 0x07..0x08 | Version (u16 = 1)  | 0x09..0x0A | Flags (u16 = 0)          |
+------------+--------------------+------------+--------------------------+
| 0x0B..0x0E | Manifest Length (u32, 小端序) = N 字节                      |
+-------------------------------------------------------------------------+
| 0x0F..0x0F+N | JSON Manifest (N 字节 UTF-8 紧凑文本):                     |
|   - module: 模块全局唯一标识 (如 "native_add")                          |
|   - abi: 原生接口协议版本 (如 "xu-c-1")                                  |
|   - exports: 导出的函数名、参数类型列表与返回值类型契约                  |
|   - slices: 各目标平台切片元数据及 SHA-256 签名散列                      |
+-------------------------------------------------------------------------+
| 切片索引表开始处 (4 Bytes): Slice Count (u32, 小端序)                      |
+-------------------------------------------------------------------------+
| 切片索引表条目 (每个切片记录一条):                                       |
|   - target_len (u16) + target_name (如 "macos-arm64", "linux-x64")      |
|   - kind_len (u8) + kind ("archive" 或 "object")                        |
|   - file_offset (u64) + file_size (u64)                                 |
|   - sha256 (32 字节二进制散列防篡改校验)                                |
+-------------------------------------------------------------------------+
| 多架构二进制切片负载数据区 (Multi-Arch Payload Slices):                  |
|   - macOS 切片:   Unix 标准 .a (含 Mach-O 原生对象 + xu.o 导出元数据)     |
|   - Linux 切片:   Unix 标准 .a (含 Linux ELF 原生对象 + xu.o 导出元数据)  |
|   - Windows 切片: 标准 .a / .lib (含 Windows COFF 原生对象 + xu.o 元数据) |
+-------------------------------------------------------------------------+

巧妙的双面兼容设计：每个平台的切片本质是一个标准的 .a 静态归档库。它将由外部原生工具链（如 C / C++ / Rust）编译出的原生业务对象（如 sqlite3.o、bridge.o），与一份格式合规并包含 Xu 导出类型签名的元数据对象（xu.o）统一打包在一起。操作系统的通用链接器直接链接这些原生的业务机器码，而 Xu 编译器则读取 xu.o 专用 .xumeta 段（Mach-O 下为 __DATA,__xumeta）中的类型契约完成编译期安全检查，两者互不干扰。

动作一：编写 C 桥接源码 (bridge.c)

包含官方头文件 xu_native.h，使用 XU_NATIVE_SYMBOL(...) 宏导出函数，自动抹平 Apple Mach-O（下划线前缀）与 Linux ELF/Windows COFF 的符号命名差异：

#include "xu_native.h"
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

// 1. int (64 位整数)
xu_int XU_NATIVE_SYMBOL(xu_native_add_add)(xu_int a, xu_int b) {
    return a + b;
}

// 2. f64 (64 位双精度浮点无损互转)
static inline double xu_to_double(xu_int bits) {
    double v; memcpy(&v, &bits, sizeof(double)); return v;
}
static inline xu_int double_to_xu(double v) {
    xu_int b; memcpy(&b, &v, sizeof(xu_int)); return b;
}
xu_int XU_NATIVE_SYMBOL(xu_native_add_scale_f64)(xu_int val_bits, xu_int factor_bits) {
    return double_to_xu(xu_to_double(val_bits) * xu_to_double(factor_bits));
}

// 3. bool (布尔判断)
uint8_t XU_NATIVE_SYMBOL(xu_native_add_is_even)(xu_int n) {
    return (n % 2 == 0) ? 1 : 0;
}

// 4. i32 (32 位有符号整数范围截断)
int32_t XU_NATIVE_SYMBOL(xu_native_add_clamp_i32)(int32_t val, int32_t min_v, int32_t max_v) {
    if (val < min_v) return min_v;
    if (val > max_v) return max_v;
    return val;
}

// 5. u32 (32 位无符号整数循环位移)
uint32_t XU_NATIVE_SYMBOL(xu_native_add_rotate_left_u32)(uint32_t val, uint32_t shift) {
    shift &= 31;
    if (shift == 0) return val;
    return (val << shift) | (val >> (32 - shift));
}

// 6. u8 (8 位无符号单字节掩码)
uint8_t XU_NATIVE_SYMBOL(xu_native_add_mask_u8)(uint8_t b, uint8_t mask) {
    return (uint8_t)(b & mask);
}

// 7. void (无返回值状态操作与副作用)
static xu_int g_counter = 0;
void XU_NATIVE_SYMBOL(xu_native_add_reset_counter)(void) { g_counter = 0; }
void XU_NATIVE_SYMBOL(xu_native_add_add_to_counter)(xu_int delta) { g_counter += delta; }
xu_int XU_NATIVE_SYMBOL(xu_native_add_get_counter)(void) { return g_counter; }

动作三：单目标切片静态编译 (xunative compile)

为各个受支持的目标平台分别生成带有元数据的 .a 切片：

# 针对 macOS Apple Silicon (ARM64)
python3 path/to/xu/scripts/xunative.py compile \
  --manifest native.json --target macos-arm64 bridge.c \
  -o native/native_add-arm64.a

# 针对 macOS Intel (x86_64)
python3 path/to/xu/scripts/xunative.py compile \
  --manifest native.json --target macos-x64 bridge.c \
  -o native/native_add-x64.a

动作四：全目标切片聚合打包 (xunative pack)

将单目标切片聚合装载为全平台自描述的便携式 .xulib 文件：

python3 path/to/xu/scripts/xunative.py pack \
  --manifest native.json \
  --slice macos-arm64=native/native_add-arm64.a \
  --slice macos-x64=native/native_add-x64.a \
  -o native/native_add.xulib

动作六：在 Xu 源码中导入与调用 (main.xu)

@main

#native_add

fn main() int {
    println("=== Xu <-> Native C Multi-Type Interop Demo ===")

    // 1. int
    sum := native_add.add(20, 22)
    println("1. int add(20, 22) = " + str(sum))

    // 2. f64
    scaled := native_add.scale_f64(1.5, 3.0)
    println("2. f64 scale_f64(1.5, 3.0) * 10 = " + str(int(scaled * 10.0)))

    // 3. bool
    println("3. bool is_even(42) = " + str(native_add.is_even(42)))

    // 4. i32
    clamped := native_add.clamp_i32(i32(150), i32(0), i32(100))
    println("4. i32 clamp_i32(150, 0, 100) = " + str(int(clamped)))

    // 5. u32
    rotated := native_add.rotate_left_u32(u32(1), u32(4))
    println("5. u32 rotate_left_u32(1, 4) = " + str(int(rotated)))

    // 6. u8
    masked := native_add.mask_u8(u8(255), u8(15))
    println("6. u8 mask_u8(255, 15) = " + str(int(masked)))

    // 7. void
    native_add.reset_counter()
    native_add.add_to_counter(100)
    c := native_add.get_counter()
    println("7. void state counter = " + str(c))

    println("=== All Native Type Assertions Passed ===")
    << 0
}

5. 常见问题解答 (FAQ)

Q：我只在本地开发单平台工具，不想打包 .xulib，可以直接用 .a 吗？
A：完全可以！直接在 xu.xun 中写 native_add: file:./native/native_add-arm64.a 或在命令行执行 xu build main.xu ./native/native_add-arm64.a 即可。注意 .a 内需包含带有导出签名的 xu.o（可使用 xunative compile 或 xunative archive 生成）。

Q：.xulib 会影响运行期性能吗？
A：完全为零开销。.xulib 仅在编译链接期工作，构建器提取切片后直接由平台链接器完成静态硬链接，生成的可执行文件与手写静态 C 链接二进制完全一致，无任何中间件代理或运行时解包负担。
