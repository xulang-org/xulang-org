原生模块与 .xulib 规范

Xu {{xu_version}} · 原生 C/C++ 互操作 · 通用 .a 与便携式 .xulib 多目标切片规范

在系统级编程中，与现有的 C/C++ 原生代码库集成是关键能力。Xu 语言提供了开箱即用的原生互操作支持。很多开发者会产生疑问：“为什么 Xu 要引入 .xulib，难道标准的通用 .a（静态库）不够用吗？”

本文档深入解析 Xu 的原生互操作机制、通用静态库与 .xulib 的分工定位、容器二进制结构以及端到端打包与链接流程。

1. 核心结论：通用 .a 与 .xulib 的关系

  • 标准通用 .a（Unix 静态归档库）原生支持且地位完全平等：你可以直接使用本地系统编译器（如 clang、gcc、msvc）编译出标准的 .a，并在命令行 xu build main.xu module.a 或 xu.xun 的 native: 中直接声明引用，底层最终由操作系统原生链接器（ld / clang / lld）静态链接。
  • .xulib 是面向跨平台生态分发的“多目标切片元数据包”：它并不是一种全新的专有机器码格式，其内部包裹的依然是各个目标平台标准的 .a 静态切片，额外附加了强类型签名契约（JSON Manifest）与 SHA-256 完整性哈希。
特性维度通用 .a 静态库便携式 .xulib 容器包
适用场景单目标平台开发、本地临时调试、私有定制 C 链接跨平台模块分发、开源生态扩展包（如 packages/sqlite）
架构支持单架构单目标（如仅 linux-x64 或仅 macos-arm64）多目标多架构统一打包（单个文件内嵌全平台切片）
跨平台切换需在配置文件或构建脚本中编写复杂的 OS/Arch 切换条件构建器自动按当前 --target 提取匹配切片，零配置透明跨平台
类型安全仅含裸符号表（Symbol Table），丢失函数参数与返回值类型内置 JSON Manifest 与 XUOBJ 契约，编译期完成强类型检查
完整性校验无内置防篡改机制每个架构切片均记录 SHA-256 校验和，解包即校验

2. 为什么通用的 .a 无法满足跨平台生态分发？

① 跨系统/跨架构的多目标切片割裂

在传统的 Unix 工具链中，.a 归档由 ar 工具生成，仅包含单一操作系统与 CPU 架构的目标对象（例如 Mach-O 只能在 macOS 上链接，ELF 只能在 Linux 上链接，PE/COFF 只能在 Windows 上链接）。

尽管 macOS 提供了 lipo 机制来制作 Universal Binary（胖二进制），但其仅限 Apple 生态内部区分 x86_64 与 arm64，无法包容 Linux 或 Windows 目标。如果没有统一容器，一个带 C 原生依赖的模块就必须分发 sqlite_linux_x64.a、sqlite_macos_arm64.a、sqlite_windows_x64.a 等一长串文件，使用方必须编写繁琐的平台条件脚本进行分流。

② 缺乏语言级函数签名与类型安全契约

C 语言编译后的符号（Symbol）只是一串函数名称（如 _sqlite3_open），不包含参数类型和返回类型信息。若没有 C 头文件，Xu 编译器无法静态验证调用参数是否匹配。错误的参数传递只能拖到链接失败或在运行时引发内存崩溃（Segmentation Fault）。

③ 消除“使用者本地必须安装 C/C++ 编译器”的强羁绊

在包分发体系中，若没有多目标预编译容器，依赖 C 代码的扩展包就只能在用户本地 xu install 或构建时即时编译。这要求每台开发机和 CI 机器都必须配置完备且版本匹配的 C 编译器、Make 工具及头文件。.xulib 允许模块维护者一次性预打包全平台切片，使用者免装 C 工具链即可开箱即用。

3. .xulib 内部结构与二进制规范

.xulib 是自描述的二进制容器（版本规范 xulib-1），其布局紧凑清晰：

+-------------------------------------------------------+
| Magic (7B): "XULIB\x01\x00"                           |
+-------------------------------------------------------+
| Version (u16=1) | Flags (u16=0) | Manifest Length (u32)|
+-------------------------------------------------------+
| JSON Manifest (UTF-8 紧凑文本)                        |
|   - module: 模块全局标识 (如 "sqlite_native")         |
|   - abi: 原生接口协议版本 (如 "xu-c-1")                |
|   - exports: 导出的函数名、参数类型列表与返回值类型    |
|   - slices: 各平台切片元数据及 SHA-256 签名           |
+-------------------------------------------------------+
| Slice Count (u32)                                     |
+-------------------------------------------------------+
| Slice 索引表条目 (每个切片一条):                      |
|   - target_len (u16) + target_name (如 "macos-arm64") |
|   - kind_len (u8) + kind ("archive" 或 "object")      |
|   - file_offset (u64) + file_size (u64)               |
|   - sha256 (32B 二进制散列)                           |
+-------------------------------------------------------+
| 负载区域 (Payload):                                   |
|   - 切片 1: 标准 Unix .a (含 Mach-O 对象 + xu.o 元数据)|
|   - 切片 2: 标准 Unix .a (含 Linux ELF 对象)          |
|   - 切片 3: 标准 .a / .lib (含 Windows COFF 对象)      |
+-------------------------------------------------------+

巧妙的双面兼容设计：切片内部不仅包含由 C 编译器生成的标准原生对象，还注入了一个专用的 .xumeta 数据段（在 Mach-O 中为 __DATA,__xumeta）。Xu 编译器能读取其中的 XUOBJ 签名，而系统的通用链接器则把该段当作普通静态数据处理，互不干扰。

4. 编译与链接流水线

源码期：编写 C 代码与 native.json
    ↓
打包期：
    xunative compile -> 针对各个目标架构分别生成 .a 切片
    xunative pack    -> 将多个目标 .a 与 native.json 封装为 module.xulib
    ↓
消费期：在项目 xu.xun 中声明依赖
    native:
      sqlite_native: file:./native/sqlite.xulib
    ↓
构建期（xu build）：
    1. 读取 Manifest -> 静态类型校验原生函数调用
    2. 根据 --target -> 提取对应平台的 .a 临时切片并验证 SHA-256
    3. 调用平台原生 Linker -> 将 Xu 目标文件与提取的 .a 静态链接为最终二进制

5. 快速上手实战

步骤 1：编写 C 桥接源码

使用官方宏 XU_NATIVE_SYMBOL 导出符号，可自动抹平不同系统在符号下划线（Mach-O 前缀 _ 与 ELF 无前缀）上的差异：

#include <stdint.h>

#if defined(__APPLE__)
#define XU_NATIVE_SYMBOL(name) _xu_native_add_##name
#else
#define XU_NATIVE_SYMBOL(name) xu_native_add_##name
#endif

int64_t XU_NATIVE_SYMBOL(add)(int64_t a, int64_t b) {
    return a + b;
}

步骤 2：编写类型元数据清单 (native.json)

{
  "module": "native_add",
  "abi": "xu-c-1",
  "exports": [
    {"name": "add", "params": ["int", "int"], "ret": "int"}
  ]
}

步骤 3：多架构切片编译与打包

# 1. 分别为目标平台编译切片
python3 path/to/xunative.py compile \
  --manifest native.json --target macos-arm64 bridge.c -o native/add-arm64.a

python3 path/to/xunative.py compile \
  --manifest native.json --target macos-x64 bridge.c -o native/add-x64.a

# 2. 汇聚打包为便携式的 .xulib
python3 path/to/xunative.py pack \
  --manifest native.json \
  --slice macos-arm64=native/add-arm64.a \
  --slice macos-x64=native/add-x64.a \
  -o native/native_add.xulib

步骤 4：在项目清单与代码中使用

在项目的 xu.xun 中声明原生模块映射：

module: my_project
version: !ver 0.1.0
xu: !ver {{xu_version}}

native:
  native_add: file:./native/native_add.xulib

在 Xu 源码中直接调用，享受强类型约束：

@main
#fmt
native_add #native_add

fn main() int {
    ans := native_add.add(20, 22)
    fmt.println("Result from C:", ans) // 42
    << 0
}

6. 常见问题解答 (FAQ)

Q：我只在本地开发单平台工具，不想打 .xulib，可以直接用 .a 吗？
A：完全可以！直接在 xu.xun 中写 native_add: file:./native/add-arm64.a 或在命令行执行 xu build main.xu ./native/add-arm64.a 即可。注意 .a 内需包含带有导出签名的 xu.o（可使用 xunative compile 或 xunative archive 生成）。

Q：.xulib 会影响运行期性能吗？
A：完全为零开销。.xulib 仅在编译链接期工作，构建器提取切片后直接由平台链接器完成静态硬链接，生成的可执行文件与手写静态 C 链接二进制完全一致，无任何中间件代理或运行时解包负担。
