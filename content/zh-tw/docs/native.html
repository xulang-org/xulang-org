原生模組與 .xulib 規範

Xu {{xu_version}} · 原生 C/C++ 互操作 · 多資料型別對映 · 通用 .a 與行動式 .xulib 多目標切片規範

在系統級軟體工程中，與成熟的 C/C++ 原生程式碼庫整合是極其關鍵的基礎能力。Xu 語言提供了零抽象成本、強型別檢查的原生互操作機制。很多開發者在初次接觸時會產生疑問：“為什麼 Xu 既支援標準通用 .a（靜態歸檔庫），又要引入行動式 .xulib？”

本文件深入解析 Xu 的原生互操作機制、通用靜態庫與 .xulib 的分工定位、支援的完整資料型別對映表以及端到端完整的 7 個開發動作。

兩種原生互操作路徑：extern "C" 與 xu native

Xu 同時保留並長期維護兩套互補的 C 原生互操作機制：直接 C FFI（extern "C" + 標準函式庫 #ffi）與靜態原生模組（xu native + include/xu_native.h）。兩者定位不同，而非新舊替代：

維度extern "C" + #ffi（直接 C FFI）xu native + include/xu_native.h（靜態原生模組）
適用場景直接呼叫現成系統庫或第三方動態庫（如 libc、libsqlite3、libSDL3、GPU / AI 驅動）封裝自有 C / C++ / Objective-C 橋接程式碼，打包為靜態 .a 或跨平臺 .xulib
膠水成本無需單獨編寫 C 膠水檔案，在 Xu 原始碼中直接宣告即可呼叫需編寫薄 C 橋接與 JSON Manifest，經 xu native 編譯歸檔
安全邊界呼叫點須在 unsafe { } 內，裸指標 c_ptr 與記憶體佈局由呼叫方保證Xu 呼叫側無需 unsafe；xu-c-2 透過借用檢查傳遞零拷貝切片（&[]int / $&[]int / &[]u8 / $&[]u8），並自動保障寫時複製（COW）
連結與分發常見用法透過動態庫（如 dlopen）載入，依賴目標機執行環境靜態連結進最終產物；.xulib 內建多平臺切片（含 iOS / Android）與 SHA-256 校驗，適合行動端與獨立分發
能力與配套支援 @repr("C")、c_callback、變參與任意 C 結構體，配套標準函式庫 #ffi收斂為受控純量與借用 span ABI，配套工具鏈 bin/xu-native 與標頭檔案 include/xu_native.h
  • 對接現成 C / 系統 / 動態庫 → 優先使用 extern "C" + #ffi。
  • 封裝自有 C / C++ / ObjC 程式碼、需要無 unsafe 零拷貝借用切片或跨平臺靜態 .xulib 分發 → 使用 xu native + include/xu_native.h（下文詳解該路徑）。

1. 核心結論：通用 .a 與 .xulib 的關係

  • 標準通用 .a（Unix 靜態歸檔庫）原生支援且地位完全平等：使用 xu native compile 或 xu native archive 將 Xu 介面後設資料與原生物件一起打包。在 macos-arm64 和 macos-x64 上，可在命令列 xu build main.xu module.a 或 xu.xun 的 native: 中直接宣告引用，底層最終由作業系統原生連結器（ld / clang / lld）靜態連結。
  • .xulib 是面向跨平臺生態分發的“多目標切片後設資料包”：它並不是一種全新的專有機器碼格式，其內部包裹的依然是各個目標平臺標準的 .a 靜態切片，額外附加了強型別簽名契約（JSON Manifest）與 SHA-256 完整性雜湊。

一步原生連結目前僅支援 macos-arm64 和 macos-x64，需要 macOS C 工具鏈。其他目標須使用 --emit-obj，將 XUOBJ 轉為平臺物件，再由外部系統連結器完成連結。容器支援多目標切片並不擴大一步連結的平臺範圍。下方七步示例使用 macOS 切片。

特性維度通用 .a 靜態庫行動式 .xulib 容器包
適用場景單目標平臺開發、本地臨時除錯、私有定製 C 連結跨平臺模組分發、開源生態擴充套件包（如 packages/sqlite）
架構支援單架構單目標（如僅 linux-x64 或僅 macos-arm64）多目標多架構統一打包（單個檔案內嵌全平臺切片）
跨平臺切換需在配置檔案或構建指令碼中編寫複雜的 OS/Arch 切換條件構建器自動按當前 --target 提取匹配切片，零配置透明跨平臺
型別安全xu native compile/archive 生成的歸檔包含 XUOBJ 匯出簽名內建 JSON Manifest 與 XUOBJ 契約，編譯期完成強型別檢查
完整性校驗無內建防篡改機制每個架構切片均記錄 SHA-256 校驗和，解包即校驗

2. 跨語言支援的資料型別與 ABI 對照

在 abi: "xu-c-1" 協議下，Xu 統一使用機器通用標量暫存器完成高效傳遞，嚴格杜絕重型膠水程式碼：

intxu_int (int64_t)64 位標準有符號整數，常用於計數、長度、索引偏移
f6464 位浮點 (IEEE-754)雙精度浮點數。標量位模式透過通用暫存器直傳，C 側藉助內聯轉換函式實現無損對映
booluint8_t / bool布林真假邏輯（1 為 true，0 為 false）
i32int32_t32 位有符號整數，用於系統 API 錯誤碼、區間截斷
u32uint32_t32 位無符號整數，用於位移操作、掩碼、雜湊與校驗和
u8uint8_t8 位無符號單位元組，用於協議解析、字元碼、單通道畫素資料
voidvoid無返回值過程，用於重置、初始化或內部有狀態副作用操作

2.1 同步借用 i64 批次資料：xu-c-2

Xu 0.11.3 新增顯式的 abi: "xu-c-2" 契約。清單引數 i64_span 對映為 Xu &[]int 及指向 xu_i64_span 的 C 指標；i64_span_mut 對映為 $&[]int 及指向 xu_i64_span_mut 的指標。匹配 SDK 的 include/xu_native.h 定義佈局：八位元組元素數量，隨後是資料指標。

每次同步呼叫提供獨立的臨時描述符。原生程式碼不得保留描述符或資料指標、修改描述符欄位、調整陣列大小或接管所有權；可寫借用僅允許修改元素。空借用的資料指標可以為空。容量和 Xu 內部描述符不跨越此邊界。

當前 C2 支援宿主 64 位目標、64 位 int 標量引數，以及 int/void 返回值，不定義浮點簽名、通用回撥或借用返回值。介面卡處理平臺引數暫存器、棧引數與 Win64 shadow space，但不擴充套件前述一步連結支援。需要傳遞原生函式值時，應透過 Xu 包裝函式使用。

C2 使用 XUOBJ version 2 與 xulib-2，容器在偏移 7 處記錄版本 2；舊產品明確拒絕此格式，C1 庫繼續相容。下方佈局圖描述 C1 容器。容器選擇與切片提取發生在構建期，C2 仍需在執行期準備呼叫臨時描述符與引數。

完整的 .xulib 二進位制容器物理欄位規範對照表：

偏移區間 (Offset) 欄位名稱 (Field) 型別與尺寸 規範定義與物理語義說明
物理段 1：固定容器檔案頭 (Fixed Container Header · 15 Bytes)
0x00..0x06 (7 Bytes) 魔數標識 (Magic) char[7] 固定為 "XULIB\x01\x00"，用於快速識別合規的 .xulib 二進位制容器並校驗主版本。
0x07..0x08 (2 Bytes) 次版本號 (Version) u16 (小端序) 容器格式次版本號，當前規範固定為 1。
0x09..0x0A (2 Bytes) 標誌位 (Flags) u16 (位掩碼) 保留供未來容器擴充套件（如壓縮、嵌入式簽名），預設填 0。
0x0B..0x0E (4 Bytes) 清單長度 (Manifest Len) u32 (小端序) 記錄緊隨其後的 JSON 契約文字總位元組數 $N$。
物理段 2：契約後設資料清單 (JSON Manifest · N Bytes)
0x0F..0x0F+N ($N$ Bytes) 契約清單 (Manifest) UTF-8 緊湊文字 xu native pack 寫出的容器頂層後設資料：
• module：全域性唯一的模組名稱空間標識（如 "native_add"）
• abi：原生介面協議規範版本（如 "xu-c-1"）
• format：容器格式標識（"xulib-1"）
• slices：記錄各目標平臺的切片名及對應的 SHA-256 簽名雜湊
物理段 3：切片索引表 (Slice Index Table)
0x0F+N 處 (4 Bytes) 切片總數 (Slice Count) u32 (小端序) 記錄索引表中連續排列的多架構目標切片數量 $M$。
連續變長索引項 切片索引表條目 (Entries) 變長連續結構體陣列 每個切片條目順序包含：
• target_len (u16) + target_name（如 "macos-arm64"、"linux-x64"）
• kind_len (u8) + kind（"archive" 靜態庫或 "object" 單物件）
• file_offset (u64) + file_size (u64) 絕對檔案偏移與切片尺寸
• sha256 (32 Bytes) 二進位制雜湊防篡改校驗碼
物理段 4：多架構二進位制切片負載 (Multi-Arch Payload Slices)
根據索引絕對偏移 macOS 切片 (Mach-O) 標準 Unix .a 包含 Mach-O 機器碼物件（如 bridge.o）+ xu.o（含 __DATA,__xumeta 符號段）。
根據索引絕對偏移 Linux 切片 (ELF) 標準 Unix .a 包含 Linux ELF 機器碼物件 + xu.o（含 .xumeta 符號段）。
根據索引絕對偏移 Windows 切片 (COFF) 標準 .a / .lib 包含 Windows COFF 機器碼物件 + xu.o（含 .xumeta 符號段）。

巧妙的雙面相容設計：每個平臺的切片本質是一個標準的 .a 靜態歸檔庫。它將由外部原生工具鏈（如 C / C++ / Rust）編譯出的原生業務物件（如 sqlite3.o、bridge.o），與一份格式合規幷包含 Xu 匯出型別簽名的後設資料物件（xu.o）統一打包在一起。作業系統的通用連結器直接連結這些原生的業務機器碼，而 Xu 編譯器則讀取 xu.o 專用 .xumeta 段（Mach-O 下為 __DATA,__xumeta）中的型別契約完成編譯期安全檢查，兩者互不干擾。

輸入 native.json 宣告 exports，各歸檔的 xu.o XUOBJ 後設資料儲存這些型別簽名。產品工具 xu native pack 不把 exports 複製到頂層清單。原始碼樹中的 Python 輔助工具 scripts/xunative.py 會複製輸入清單，因此其輸出保留 exports。讀取方應從切片後設資料獲取介面，不能要求頂層必有匯出表。

動作一：編寫 C 橋接原始碼 (bridge.c)

包含官方標頭檔案 xu_native.h，使用 XU_NATIVE_SYMBOL(...) 宏匯出函式，自動抹平 Apple Mach-O（下劃線字首）與 Linux ELF/Windows COFF 的符號命名差異：

#include "xu_native.h"
#include <stdint.h>
#include <stdbool.h>
#include <string.h>

// 1. int (64 位整數)
xu_int XU_NATIVE_SYMBOL(xu_native_add_add)(xu_int a, xu_int b) {
    return a + b;
}

// 2. f64 (64 位雙精度浮點無損互轉)
static inline double xu_to_double(xu_int bits) {
    double v; memcpy(&v, &bits, sizeof(double)); return v;
}
static inline xu_int double_to_xu(double v) {
    xu_int b; memcpy(&b, &v, sizeof(xu_int)); return b;
}
xu_int XU_NATIVE_SYMBOL(xu_native_add_scale_f64)(xu_int val_bits, xu_int factor_bits) {
    return double_to_xu(xu_to_double(val_bits) * xu_to_double(factor_bits));
}

// 3. bool (布林判斷)
uint8_t XU_NATIVE_SYMBOL(xu_native_add_is_even)(xu_int n) {
    return (n % 2 == 0) ? 1 : 0;
}

// 4. i32 (32 位有符號整數範圍截斷)
int32_t XU_NATIVE_SYMBOL(xu_native_add_clamp_i32)(int32_t val, int32_t min_v, int32_t max_v) {
    if (val < min_v) return min_v;
    if (val > max_v) return max_v;
    return val;
}

// 5. u32 (32 位無符號整數迴圈位移)
uint32_t XU_NATIVE_SYMBOL(xu_native_add_rotate_left_u32)(uint32_t val, uint32_t shift) {
    shift &= 31;
    if (shift == 0) return val;
    return (val << shift) | (val >> (32 - shift));
}

// 6. u8 (8 位無符號單位元組掩碼)
uint8_t XU_NATIVE_SYMBOL(xu_native_add_mask_u8)(uint8_t b, uint8_t mask) {
    return (uint8_t)(b & mask);
}

// 7. void (無返回值狀態操作與副作用)
static xu_int g_counter = 0;
void XU_NATIVE_SYMBOL(xu_native_add_reset_counter)(void) { g_counter = 0; }
void XU_NATIVE_SYMBOL(xu_native_add_add_to_counter)(xu_int delta) { g_counter += delta; }
xu_int XU_NATIVE_SYMBOL(xu_native_add_get_counter)(void) { return g_counter; }

動作三：單目標切片靜態編譯 (xu native compile)

為各個受支援的目標平臺分別生成帶有後設資料的 .a 切片：

mkdir -p native

# 針對 macOS Apple Silicon (ARM64)
xu native compile \
  --manifest native.json --target macos-arm64 bridge.c \
  -o native/native_add-arm64.a

# 針對 macOS Intel (x86_64)
xu native compile \
  --manifest native.json --target macos-x64 bridge.c \
  -o native/native_add-x64.a

動作四：全目標切片聚合打包 (xu native pack)

將單目標切片聚合裝載為全平臺自描述的行動式 .xulib 檔案：

xu native pack \
  --manifest native.json \
  --slice macos-arm64=native/native_add-arm64.a \
  --slice macos-x64=native/native_add-x64.a \
  -o native/native_add.xulib

你還可以透過 xu native inspect native/native_add.xulib 檢視容器切片列表與 SHA-256 摘要，或使用 xu native extract 單獨提取切片。

動作五：在工程專案配置中宣告原生模組 (xu.xun)

module: my_project
version: !ver 0.1.0
xu: !ver {{xu_version}}

native:
  native_add: file:./native/native_add.xulib

動作六：在 Xu 原始碼中匯入與呼叫 (main.xu)

@main

#native_add

fn main() int {
    println("=== Xu <-> Native C Multi-Type Interop Demo ===")

    // 1. int
    sum := native_add.add(20, 22)
    println("1. int add(20, 22) = " + str(sum))

    // 2. f64
    scaled := native_add.scale_f64(1.5, 3.0)
    println("2. f64 scale_f64(1.5, 3.0) * 10 = " + str(int(scaled * 10.0)))

    // 3. bool
    println("3. bool is_even(42) = " + str(native_add.is_even(42)))

    // 4. i32
    clamped := native_add.clamp_i32(i32(150), i32(0), i32(100))
    println("4. i32 clamp_i32(150, 0, 100) = " + str(int(clamped)))

    // 5. u32
    rotated := native_add.rotate_left_u32(u32(1), u32(4))
    println("5. u32 rotate_left_u32(1, 4) = " + str(int(rotated)))

    // 6. u8
    masked := native_add.mask_u8(u8(255), u8(15))
    println("6. u8 mask_u8(255, 15) = " + str(int(masked)))

    // 7. void
    native_add.reset_counter()
    native_add.add_to_counter(100)
    c := native_add.get_counter()
    println("7. void state counter = " + str(c))

    println("=== All Native Type Assertions Passed ===")
    << 0
}

Linux x64 外部連結

安裝 Clang 與歸檔工具後，使用 xu native compile --manifest native.json --target linux-x64 bridge.c -o native_add-linux.a 準備 linux-x64 歸檔。使用上面的 main.xu 和該歸檔，輸出 XUOBJ，再用匹配 SDK 的內部輔助命令 _elf_o 轉換並外部連結：

xu build main.xu native_add-linux.a --target linux-x64 --emit-obj -o main.xuobj
xu _elf_o main.xuobj main.o
cc -nostartfiles -no-pie main.o native_add-linux.a -o app
./app

Xu 提供自己的入口點，因此此 Linux 連結命令省略 C 啟動檔案。Windows 和其他目標須使用對應的物件轉換工具、入口點及執行庫連結選項；上述 Linux 命令僅適用於 Linux x64。

5. 常見問題解答 (FAQ)

Q：我只在本地開發單平臺工具，不想打包 .xulib，可以直接用 .a 嗎？
A：在上述 macOS 目標上可以。直接在 xu.xun 中寫 native_add: file:./native/native_add-arm64.a 或在命令列執行 xu build main.xu ./native/native_add-arm64.a 即可。注意 .a 內需包含帶有匯出簽名的 xu.o（可使用 xu native compile 或 xu native archive 生成）。

Q：.xulib 會影響執行期效能嗎？
A：容器在構建期處理，不需要執行時解包器；選中的原生切片直接連結到應用。C2 呼叫仍須準備借用描述符與平臺引數，容器提取不會消除這些 ABI 適配工作。
