什麼是 Xu 程式語言？

Xu 是一門靜態型別系統程式語言，採用自研原生與 WebAssembly AOT 後端。它結合所有權推斷、借用檢查與確定性資源釋放，無需垃圾回收器，並內建協程（xu f()）與型別安全通道（chan T）。它既可用於構建高並發網路服務與跨平臺原生桌面 UI，也原生支援無宿主裸機韌體與作業系統微核心開發。

Xu 編譯器是否使用了 LLVM？為什麼採用自研後端？

沒有使用 LLVM。Xu 編譯器採用自研 MIR（中間表示）、暫存器分配器及面向 Mach-O、ELF、PE 與 WebAssembly 的程式碼發射器。原生模組與桌面構建可能需要宿主庫及匹配的 C 工具鏈；詳見原生模組與桌面構建要求。

Xu 語言是否有垃圾回收（GC）？

沒有。Xu 透過所有權推斷與 RAII 在作用域退出時確定性釋放資源，不相依性執行時垃圾回收器。所有權檢查及 &T 共享借用 / $&T 獨佔借用檢查，可防止受檢查 Xu 程式碼中的一類生命週期與別名訪問錯誤。

併發程式碼中的共享可變狀態仍需適當同步。原生程式碼、FFI 與併發庫各有安全要求；這些檢查不保證所有程式都沒有資料競爭、洩漏或未定義行為。分配、排程與 I/O 仍可能造成延遲波動。詳見所有權與借用、併發和原生模組邊界。

Xu 相比 Rust 與 Go 有哪些區別？

Xu 推斷所有權並確定性釋放資源，無需顯式生命週期標註（如 <'a>）。它提供類似 Go 的協程與型別安全通道，以所有權和借用檢查替代垃圾回收器。在底層與核心開發方面，Go 強綁定 GC 與龐大執行環境而無法直接編寫裸機微核心；Rust 雖支援 no_std，但在複雜系統開發中常面臨繁瑣的生命週期標註；Xu 則透過 profile: freestanding 無宿主模式與純靜態 #core 庫提供零 GC 原生開發體驗，同時保持免生命週期標註的人性化語法，將底層硬體操作嚴格限制在 unsafe 隔離邊界內。安全限制見上文邊界說明；執行時間與記憶體的實測結果見基準看板。

Xu 如何支援作業系統核心與裸機韌體開發？

原生支援從零編寫作業系統微核心、裸機韌體與硬體驅動程式。不同於依賴執行階段垃圾回收（GC）的託管語言，也不同於需要複雜顯式生命週期標註的語言，Xu 採用嚴格分層的底層系統架構：

  • 在普通系統組件與核心服務邏輯中，嚴格保留隱式所有權推斷與編譯期確定性解構，無需垃圾回收器也無須手寫 <'a> 生命週期標註；
  • 在最底層的硬體互動（約佔 5% 程式碼）中，透過無宿主模式（freestanding）、裸指標（*raw T）、易失訪存屏障（volatile_read / volatile_write）與純靜態核心庫（#core）進行精確受控的微架構操縱。

核心範例與規範可參考官方 kernel_poc 概念驗證專案與 Xu 0.14.0 發布公告。

什麼是無宿主模式（Freestanding Profile）？如何徹底阻斷外部 OS 相依性？

無宿主模式指編譯產物完全不依賴外部作業系統核心的系統呼叫（Syscalls）、動態連結器以及 C 執行階段程式庫（libc）。Xu 提供三級宣告機制：

  • 原始碼級標記：原始檔首行宣告 $freestanding 編譯標籤；
  • 專案級清單：在專案設定檔 xu.xun 中宣告 profile: freestanding；
  • 命令列引數：編譯時傳入 --profile=freestanding 或 --no-std。

開啟該模式後，編譯器將徹底剝離宿主 OS 執行環境、預設協程排程器與標準 I/O 執行環境，直接輸出純淨獨立的裸機 ELF / PE 映像，產物尺寸通常僅 1.9 KB ~ 2.4 KB。

在沒有標準庫的裸機環境下，Xu 提供哪些核心硬體抽象與並發原語？

Xu 交付了純靜態、零系統呼叫、零隱式分配的核心基礎庫 #core，包含現代核心研發的必備模組：

  • #core/arch：CPU 特權指令（cli、sti、hlt、pause、wfi）、控制暫存器存取（CR0/CR2/CR3/CR4、VBAR、SCTLR）、8259A PIC 中斷晶片重對映、8254 PIT 可程式化定時器初始化及 IDT 中斷門描述符載入（load_idt）；
  • #core/sync：提供中斷安全自旋鎖 IrqSpinlock 與普通自旋鎖 Spinlock，配合 RAII 守衛（IrqGuard、SpinGuard）實現作用域退出時確定性解鎖並自動恢復 CPU 中斷旗標位（EFLAGS / PSTATE），即使在核心中斷上下文也保證零洩漏與無死鎖；
  • #core/task：跨架構 192 位元組 16 位元組對齊的微任務上下文結構 TaskContext、原子級硬體上下文切換（switch_context）、TrapFrame 異常現場快照與系統呼叫分發入口；
  • #core/virtio：純靜態 VirtIO MMIO 驅動框架、VirtQueue 描述符環、VirtioBlkDriver 磁碟區塊裝置與 VirtioNetDriver 虛擬網路卡驅動；
  • #core/mem 與 #core/alloc：零相依記憶體原語（memset/memcpy/memcmp）與可插拔全域分配器契約 GlobalAlloc，可直接接入夥伴系統（Buddy System）或 Slab 分配器。

核心中如何安全地進行實體記憶體映射（MMIO）與裸指標操作？

硬體暫存器與週邊記憶體存取要求精確受控的語法屏障：

  • 裸指標型別 *raw T 與 unsafe { ... } 區塊：允許進行絕對實體位址重解釋與指標算術，但解引用必須強制包裹在 unsafe { ... } 隔離區塊中。所有權推斷跳過裸指標，確保底層危險操作不污染上層核心業務邏輯；
  • 易失訪存屏障（Volatile MMIO）：提供內建 volatile_read 與 volatile_write 原語，防止編譯器最佳化通道將其作為無用程式碼消除（DCE）或進行迴圈不變量外提（LICM）；
  • 精確記憶體佈局控制：支援 @repr("C", align: N)（如 4KB 頁面對齊 @repr("C", align: 4096) 用於 PML4 頁表）和 @repr("C", packed) 緊湊排布（用於硬體協定幀與描述符）；
  • 鷹架與模擬整合：使用 xu init --baremetal my_os 一鍵生成多架構核心專案、連結腳本（linker.ld）與 Makefile，並透過 make qemu 即可在 QEMU 模擬器中直接引導執行。

Xu 支援原生桌面 UI 嗎？必須使用 WebView 嗎？

支援，而且 WebView 是可選項。當前 Xu {{xu_version}} 正式 SDK 提供兩種介面方式：使用 #ui/draw、#ui/layout 和 #ui/widgets 編寫原生繪圖與控制元件介面；或使用 #ui/webview 承載 HTML/CSS/JavaScript，透過請求橋接與 Xu 互動。原生控制元件示例不需要 HTML、CSS 或 JavaScript。

#ui 提供視窗、事件、選單、托盤、多視窗、剪貼簿和檔案對話方塊等桌面服務。控制元件由 Xu 在原生 Canvas 上繪製，系統選單與對話方塊使用宿主外觀。入口見UI / WebView 開發指南和控制元件 API 與示例。

UI 有哪些控制元件？支援中文輸入和主題嗎？

SDK 包含按鈕、勾選框、開關、單選、滑塊、步進器、標籤頁、列表與選擇器；Input / TextArea 支援原生文字輸入會話、IME、選區及複製貼上。還提供 Table、TreeView、Pagination、ComboBox、MultiSelect、DatePicker、TimePicker、ColorPicker，以及 Popover、Tooltip、Toast、Modal 等元件。

桌面 UI 支援哪些平臺？需要安裝什麼？

桌面宿主覆蓋 macOS、Windows 和 Linux。macOS 使用 AppKit，網頁使用 WebKit；Windows 使用原生宿主，網頁需要 WebView2；Linux 使用 GTK4，網頁另需 WebKitGTK 6.0。構建與打包需要對應平臺的宿主工具鏈；原生繪圖與控制元件不要求應用嵌入 WebView。

先執行 xu doctor --desktop 檢查相依性，使用 WebView 時再加 --webview。應用目錄包含 xu.xun、main.xu 與應用圖示，使用 xu build <AppDir> --desktop 打包；完整命令見構建指南。編譯器支援某個目標不等於桌面 UI 已在該目標完成執行驗收；瀏覽器 WASM 演練場不執行桌面 UI。範圍見限制與現狀。

原生 UI 目前有哪些能力邊界？

現有元件覆蓋常用桌面互動，仍有明確邊界：Input / TextArea 是純文字編輯器；Table 為有界資料表，排序與取數由應用處理；列表與樹不提供按需構建的無界資料虛擬化。富文字、高階表格、拖拽工作區與完整輔助技術橋接仍需進一步開發。

平臺文字排版、IME 與系統服務也需要在真實目標系統上驗收，不能以跨平臺編譯透過代替互動驗證。選用元件前請檢視對應 API 契約和示例說明。

Xu 支援哪些編輯器？如何啟用 LSP？

官方 vscode-xu 擴充套件支援 VS Code 與 Cursor，透過 xu lsp 啟動 SDK 中的 xu-lsp 語言伺服器，提供實時診斷、程式碼補全、跳轉定義、懸停文件、符號大綱、查詢引用、重新命名與格式化。

其他支援 LSP 的編輯器也可配置 xu lsp 作為伺服器命令，透過標準輸入輸出（stdin/stdout）交換 JSON-RPC 2.0 訊息。通常由編輯器自動啟動；可用 xu lsp --help 檢視幫助。

xu get 與 xu install 有什麼區別？

在已有 xu.xun 的專案根目錄執行 xu get <module>@<version>，即可新增或更新指定相依性：自動修改清單中的 require:、安裝原始碼到 vendor/ 並更新 xu.lock。請將佔位符替換為真實模組與已確認釋出的 SemVer 標籤，不接受 @latest。官方擴充套件包請使用 SDK 內建包或匹配的固定原始碼提交，再執行 xu install。

xu install 則安裝清單中已經宣告的相依性。兩者均支援 --offline；需要嚴格按現有鎖檔案構建時，使用 xu build . --frozen。詳見模組與相依性；官方 packages 倉庫提供 29 個擴充套件包。

如何用 xu native 整合 C 程式碼？

xu native 提供完整的原生模組流程：xu native compile 將 C 原始碼與介面後設資料編譯為 .a；xu native archive 為已有目標檔案封裝後設資料；xu native pack 將不同目標的切片打包為 .xulib；xu native inspect 與 xu native extract 用於檢查和提取切片。

.a 用於單目標靜態庫，.xulib 用於攜帶介面契約與多個目標切片的分發。在 macos-arm64 或 macos-x64 上，構建時可直接傳入庫，例如 xu build main.xu native/mylib.xulib -o app。其他目標須輸出並轉換 XUOBJ，再外部連結。編譯 C 原始碼需安裝相應的 C 編譯工具鏈。引數與完整示例見原生模組與 .xulib 規範，或執行 xu native compile --help。

Xu 目前支援哪些作業系統與 CPU 晶片架構？

程式碼發射目標包括 macOS arm64/x64、Linux arm64/x64/loongarch64/riscv64、Windows x64/arm64 與 WebAssembly（wasm32-wasi）。在無宿主裸機與作業系統核心開發領域，支援透過 --profile=freestanding 阻斷宿主 syscall 與 libc 相依性，直接生成面向 x86_64、aarch64 與 riscv64 的純淨裸機 ELF 核心映像。可下載的 SDK 資產見下載頁。程式碼可發射、SDK 可下載不代表執行環境或 GUI 行為已實測；沒有目標機驗收結果的路徑仍屬待驗。請按所需目標查閱狀態與逐包限制。

什麼是 XACP？

XACP（Xu Agent Control Protocol）是用 xu build --xacp 和/或 --xacp-port PORT 構建的 hosted native 程式的幀控制通道。該構建會嵌入發現資訊。./app --xacp-help 印表機器可讀摘要，其中 capabilities 為 stdio，並標明 TCP 是否啟用以及繫結地址。這取代了早先只含 help-only 的發現文字。

#xacp（src/xacp）是與傳輸無關的安全核心：幀與 XUN 校驗、許可權、會話生命週期。單獨匯入 #xacp 不會裝上啟動期控制入口。stdio 與本機迴環 TCP 是 --xacp 構建插入的執行時鉤子。啟動器是 xu xacp，它轉而執行伴生工具 xu-xacp。模式為 inspect、run、debug、record、control、attach、connect。API 已包含在正式 {{xu_version}} SDK 提取結果中，契約依據對應釋出原始碼。原生會話和平臺/UI 執行驗收仍待驗。見命令列參考、#xacp API與對應釋出原始碼。

XACP 的 stdio 與本機迴環 TCP 有什麼區別？

stdio。用 --xacp-stdio 啟動目標，或執行 xu xacp control <program>。會話獨佔 stdin 與 stdout。幀使用 XACP/1\n<N>\n，後接恰好 N 個 UTF-8 位元組的純 XUN 正文。正文換行計入，字首不計入；沒有結束分隔符。傳輸層去掉字首後才呼叫 parse_frame，見精確位元組示例。業務 main 不會執行。

本機迴環 TCP。用 --xacp-port N 構建，N 為 1..65535，然後執行 <app> --xacp-tcp。程序只監聽 127.0.0.1:N。另一個終端執行 xu xacp connect PORT，逐幀中繼同樣的請求與響應。埠 0 關閉 TCP（發現資訊為 tcp: disabled (port 0)），stdio 能力仍然保留。每個已接受的連線是獨立會話。連線按順序處理；失敗的對端只結束自己的會話，監聽繼續。stdio 會話結束時程序退出。-- 之前的第一個控制標誌優先。普通啟動不監聽，也不讀取控制 stdin。

xacp.hello 會授予什麼許可權？

控制會話開始時沒有許可權，首個請求必須是 xacp.hello，攜帶 id: !i 1、ver: !ver 1.0.0 和非空 nonce。宿主未設定非空 XU_XACP_TOKEN 時，允許的許可權僅為 PERM_INFO（1），即使客戶端提供 token 或宿主設定了 XU_XACP_ALLOW_RAW=1 也不例外。配置非空 token 後，hello 必須透過 token 提供它，並由 crypto/subtle.constant_time_compare 做常數時間比較；缺失、為空或不匹配均返回 auth_failed 並關閉會話。匹配時預設允許掩碼 15，只有宿主精確設定 XU_XACP_ALLOW_RAW=1 才允許 31。可選的 permissions: !i 0..31 用於請求許可權，實際授予 requested & allowed；省略時請求整個允許掩碼。

development 許可權是顯式宿主策略，stdio 與 TCP 傳輸不會自動開啟；進入 OPEN 後許可權不可再更改，schema、幀大小、視窗與生命週期檢查仍然適用。預設啟用的 nonce 重放檢查在認證和許可權校驗後執行；檢測到重放時返回同一請求 id 的 nonce_replay，清除會話並斷開，不進入 OPEN。成功幀含整數 id: !i 和 ok: !b true，其 data 含 state: OPEN、經路徑過濾並加引號的 nonce、實際授予的整數 permissions: !i 與 permission_label：掩碼 0 為 none，1 為 info，31 為 development，其餘為 custom。proc.output 是否可用取決於宿主的輸出捕獲支援，不相依性 Screen；獨佔啟動介面卡沒有註冊 Screen，授權後的 UI 操作返回 not_implemented，應用呼叫 attach API 後註冊並持續 poll Screen，UI 操作便可經 Screen marshal 處理，能力邊界見下文。

xu xacp control 與 xu xacp run 有什麼區別？

xu xacp run <program> -- args... 會啟動程式，業務 main 會執行。工具會再插入一個 --，因此名為 --xacp-help 的業務引數不會觸發發現。debug 先列印 --xacp-help，再按同樣方式執行。它不是斷點偵錯程式。record 在 Unix 上流式輸出最多 1 MiB 的 stdout，stderr 仍留給終端。該輸出不是 XACP UI 錄製，Windows 上的 record 仍不可用。inspect 執行 --xacp-help，不接受業務引數，但同樣會執行目標程式。

control 啟動 --xacp-stdio，繼承呼叫方的 stdin 與 stdout，跳過業務 main，並且不接受業務引數。connect PORT 不接收程式路徑，只把幀中繼到 127.0.0.1:PORT。run、debug、record 的使用者引數必須寫在工具自己的 -- 之後。

XACP 目前有哪些安全限制？

啟動器只應指向受信任的本地可執行程式。inspect 也會執行它。沒有 TLS，也不能繫結 127.0.0.1 以外的地址。生成器只允許 hosted native 可執行程式：庫、共享物件、測試腳手架、嵌入式目標和 --desktop 都會被拒絕。未設定非空 XU_XACP_TOKEN 時僅允許 INFO 只讀訪問；需要控制能力時須設定 XU_XACP_TOKEN。

獨佔啟動介面卡（--xacp-stdio、--xacp-tcp 或 xu xacp control）跳過業務 main，沒有註冊 Screen，授權後的 UI 操作返回 not_implemented。庫函式 xacp.attach_stdio() / xacp.attach_tcp(port) 讓應用 main 執行，由應用註冊 Screen 並持續呼叫 xacp.poll；ui.tree、ui.screenshot、ui.input、ui.act、ui.record 經 Screen marshal 訪問真實介面。Screen 關閉或登出後，等待中的請求返回 stale_window，後續 UI 請求返回 not_implemented。xu xacp attach <program> -- args... 以安全的 -- 引數邊界啟動應用，應用程式碼仍需呼叫 attach API。

按 dev 協議，已註冊 Screen 時，ui.record 在單次請求內完成有界 XAR1 取樣，返回 mode、records、bytes、truncated 和 payload。請求需提供正數 win 與 mode: events|frames，可選 max_bytes、max_records、duration_ms。客戶端重複請求拉取後續片段；每次請求只有一個響應，不保留跨請求錄製狀態或續傳遊標。stream_required 僅保留給無 sink/取樣能力的介面卡，內建 Screen 取樣路徑不返回它。

events 目前是帶 state=true 的當前 window/canvas/generation/open 狀態觀測，沒有真實輸入事件日誌；取樣不注入輸入，也不推進應用事件迴圈。frames 僅返回尺寸且 redacted=true，不含畫素。CLI xu xacp record 錄製的是 stdout，與 ui.record 的 UI 取樣不同。引數邊界、截斷和錯誤語義見 API 錄製說明。

proc.output 在啟用 --xacp 插樁的 64 位 POSIX 生成宿主上捕獲 Xu 執行時 print / eprint 與執行時 fd-write 路徑的 fd 1/2 寫入，不捕獲外部原生程式碼或子程序的寫入。Windows 與未插樁構建返回 not_implemented；僅呼叫 attach API 不會增加輸出捕獲能力。

XU_XACP_WRITE_TIMEOUT_MS 預設 10000 ms，範圍 1..600000；按每個完整出站幀計時，部分寫入進度不續期。超時視為傳輸失敗，不再傳送幀並關閉會話：獨佔 stdio 非零退出，TCP 只斷開該對端並繼續監聽；stderr 列印 xacp: write timed out after W ms，W 為配置值。Windows 管道或控制檯 stdio 的寫超時僅盡力生效，阻塞寫入仍可能無界等待。

寫超時與讀側 XU_XACP_HELLO_TIMEOUT_MS（預設 5000 ms）、XU_XACP_IDLE_TIMEOUT_MS（預設 60000 ms，0 關閉）及 attach UI 等待的 XU_XACP_REQUEST_TIMEOUT_MS（預設 5000 ms）相互獨立。xu xacp connect 自身沒有應用級響應截止，整體程序超時仍由呼叫方負責。完整契約見#xacp API與XACP 協議規格。
