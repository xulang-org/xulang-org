Native Modules & .xulib Specification

Xu {{xu_version}} · Native C/C++ Interoperability · Generic .a Archives and Portable .xulib Multi-Target Slices

In systems programming, integrating with existing C/C++ libraries is a foundational requirement. Xu provides first-class native interoperability. Developers frequently ask: "Why does Xu introduce .xulib? Isn't the standard generic .a (static archive) sufficient?"

This document details Xu's native interoperability design, clarifying the roles of generic static libraries versus .xulib, internal binary container specifications, and the end-to-end build and link pipelines.

1. Core Conclusion: Generic .a vs. .xulib

  • Standard Generic .a (Unix Static Archives) are fully supported as first-class citizens: You can compile standard .a archives with system compilers (such as clang, gcc, or msvc) and link them directly via xu build main.xu module.a or the native: section in xu.xun. Final assembly is performed by your host linker (ld, clang, or lld).
  • .xulib is a "Multi-Target Slice Container with ABI Manifest" designed for cross-platform distribution: It is not a proprietary machine-code format. Internally, it bundles standard, platform-native .a archive slices, augmented with strongly-typed manifest contracts (JSON Manifest) and cryptographic SHA-256 integrity checks.
DimensionGeneric .a ArchivePortable .xulib Container
Primary Use CaseSingle-target development, local ad-hoc debugging, private C integrationCross-platform ecosystem distribution, reusable libraries (e.g. packages/sqlite)
Architecture ScopeSingle target/architecture only (e.g., linux-x64 only or macos-arm64 only)Unified multi-target packaging (bundles all target slices in a single file)
Platform SwitchingRequires manual OS/Arch matrix switching in build scriptsCompiler automatically selects the slice matching --target transparently
Type SafetyBare symbol table only; parameter and return types are lostEmbedded JSON Manifest & XUOBJ metadata for compile-time type verification
Integrity VerificationNo built-in tamper checkEach slice is verified against its embedded SHA-256 digest upon extraction

2. Why Generic .a Fails at Cross-Platform Package Distribution

① Fragmentation Across Systems and Architectures

Traditional Unix .a archives created by ar contain object files for only one operating system and CPU architecture (Mach-O on macOS, ELF on Linux, PE/COFF on Windows). While Apple provides Universal Binaries via lipo, it only works within the Apple ecosystem. Without a unified container, a native library author would have to distribute distinct files like sqlite_linux_x64.a, sqlite_macos_arm64.a, and sqlite_windows_x64.a, forcing consumers to write complex platform dispatch logic.

② Lack of Function Signatures and Type Safety Contracts

C symbol tables contain only symbol names (e.g. _sqlite3_open). Without header files, the compiler cannot verify whether function parameters or return types match at compile time, leading to silent link errors or runtime memory corruptions. .xulib embeds type metadata directly in the artifact.

③ Eliminating Local Toolchain Prerequisites for Consumers

Without precompiled multi-target archives, distributing native dependencies forces consumers to compile C code locally during xu install, requiring pre-installed C compilers and header files. .xulib enables package maintainers to publish precompiled multi-platform slices, delivering true zero-dependency installation.

3. .xulib Internal Binary Structure

.xulib is a self-describing binary container (specification xulib-1):

+-------------------------------------------------------+
| Magic (7B): "XULIB\x01\x00"                           |
+-------------------------------------------------------+
| Version (u16=1) | Flags (u16=0) | Manifest Length (u32)|
+-------------------------------------------------------+
| JSON Manifest (UTF-8 compact text)                    |
|   - module: Module identity (e.g. "sqlite_native")     |
|   - abi: Native ABI protocol version (e.g. "xu-c-1")   |
|   - exports: Exported functions, param & return types  |
|   - slices: Target slice descriptors and SHA-256 sums  |
+-------------------------------------------------------+
| Slice Count (u32)                                     |
+-------------------------------------------------------+
| Slice Table Entries (one per target):                 |
|   - target_len (u16) + target_name (e.g. "macos-arm64")|
|   - kind_len (u8) + kind ("archive" or "object")      |
|   - file_offset (u64) + file_size (u64)               |
|   - sha256 (32B binary hash)                          |
+-------------------------------------------------------+
| Payload Area:                                         |
|   - Slice 1: Standard Unix .a (Mach-O + xu.o metadata)|
|   - Slice 2: Standard Unix .a (Linux ELF objects)     |
|   - Slice 3: Standard .a / .lib (Windows COFF objects)|
+-------------------------------------------------------+

Clever Dual Compatibility Design: Slices contain standard object files compiled by host C compilers, but also embed a dedicated .xumeta section (in Mach-O: __DATA,__xumeta). The Xu compiler reads the XUOBJ metadata from this section, while standard host linkers treat it as passive static data.

4. Compilation & Link Pipeline

Source Phase: Write C bridge sources and native.json
    ↓
Packaging Phase:
    xunative compile -> Compile individual .a slices per architecture
    xunative pack    -> Bundle slices and native.json into module.xulib
    ↓
Consumption Phase: Declare in project xu.xun
    native:
      sqlite_native: file:./native/sqlite.xulib
    ↓
Build Phase (xu build):
    1. Read Manifest -> Verify types for native function calls
    2. Match --target -> Extract matching .a slice and verify SHA-256
    3. Invoke Host Linker -> Statically link Xu objects with extracted .a

5. Quick Start Example

Step 1: Write C Bridge Source

#include <stdint.h>

#if defined(__APPLE__)
#define XU_NATIVE_SYMBOL(name) _xu_native_add_##name
#else
#define XU_NATIVE_SYMBOL(name) xu_native_add_##name
#endif

int64_t XU_NATIVE_SYMBOL(add)(int64_t a, int64_t b) {
    return a + b;
}

Step 2: Define Type Metadata (native.json)

{
  "module": "native_add",
  "abi": "xu-c-1",
  "exports": [
    {"name": "add", "params": ["int", "int"], "ret": "int"}
  ]
}

Step 3: Compile Slices and Pack into .xulib

# 1. Compile target slices
python3 path/to/xunative.py compile \
  --manifest native.json --target macos-arm64 bridge.c -o native/add-arm64.a

python3 path/to/xunative.py compile \
  --manifest native.json --target macos-x64 bridge.c -o native/add-x64.a

# 2. Pack slices into portable .xulib
python3 path/to/xunative.py pack \
  --manifest native.json \
  --slice macos-arm64=native/add-arm64.a \
  --slice macos-x64=native/add-x64.a \
  -o native/native_add.xulib

Step 4: Use in Project

Declare the native mapping in xu.xun:

module: my_project
version: !ver 0.1.0
xu: !ver {{xu_version}}

native:
  native_add: file:./native/native_add.xulib

Invoke in Xu code with type safety:

@main
#fmt
native_add #native_add

fn main() int {
    ans := native_add.add(20, 22)
    fmt.println("Result from C:", ans) // 42
    << 0
}

6. Frequently Asked Questions (FAQ)

Q: Can I use plain .a directly if I only target one platform locally?
A: Yes! You can specify native_add: file:./native/add-arm64.a in xu.xun or pass it on the command line via xu build main.xu ./native/add-arm64.a.

Q: Does .xulib introduce runtime overhead?
A: Zero runtime overhead. .xulib operates purely at compile/link time. The extracted slice is statically linked by the platform linker, producing the exact same binary output as manual static linking.
