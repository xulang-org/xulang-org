Frequently Asked Questions (FAQ)

Core answers on Xu language design, memory model, compilation architecture, LSP editor support, dependency management, native interoperability, and the XACP control channel

What is the Xu programming language?

Xu is a modern, statically typed, hypersonic AOT-compiled systems programming language designed for high-concurrency cloud-native backends, network infrastructure, and low-latency systems. Without garbage collection (Zero GC), Xu achieves memory safety and concurrency throughput through deterministic RAII ownership, first-class coroutines (xu f()), and channels (chan T).

Does the Xu compiler use LLVM? Why a custom native backend?

No, Xu does not use LLVM. The compiler features a custom-built lightweight MIR (Middle Intermediate Representation), register allocator, and direct native code emitters targeting Mach-O, ELF, PE, and WebAssembly directly. LLVM's massive pass pipeline is a primary cause of slow C++/Rust builds; Xu targets Go-like sub-second compilation speeds with a self-contained zero-dependency binary.

Does Xu use a garbage collector (GC)?

No. Xu has zero runtime GC overhead and no Stop-The-World (STW) pauses. Memory is managed deterministically through compile-time single-ownership tracking and RAII scoping drops, complemented by static shared (&T) and exclusive (&mut T) borrow checking that completely eliminates data races, memory leaks, and dangling pointers.

How does Xu compare to Rust and Go?

Compared to Rust, Xu delivers deterministic zero-cost memory safety without complex lifetime annotations (such as <'a>), offering first-class coroutines and channels without heavy async runtimes. Compared to Go, Xu compiles to true zero-GC native machine code without runtime STW latency, baseline memory bloat, or background GC threads.

How fast are Xu's compilation speed and runtime throughput?

Reproducible performance measurements: compare Xu with C, Rust, Go, and Swift across 47 workloads on six ARM64 and x86-64 platforms. The benchmark dashboard reports per-platform runtime, CPU time, peak memory and binary size; C and Rust use the lowest measured O1–O3 median for each workload. Compilation timings are available in the source CI reports.

Does Xu support WebAssembly (WASM) out of the box?

Yes, first-class native support. The compiler directly emits wasm32 binary modules (xu build --target wasm32) without Emscripten or external dependencies. The interactive in-browser Playground compiles the Xu compiler itself directly to WebAssembly to run client-side.

Which editors support Xu, and how do I enable LSP?

The official vscode-xu extension supports VS Code and Cursor. It runs xu lsp to launch the SDK's xu-lsp language server for diagnostics, completion, go-to-definition, hover documentation, document symbols, references, rename, and formatting.

Other LSP-compatible editors can configure xu lsp as their server command, communicating over stdin/stdout using JSON-RPC 2.0. The editor normally starts the server automatically; run xu lsp --help for help.

What is the difference between xu get and xu install?

In a project directory containing xu.xun, run xu get github.com/xulang-org/packages@v0.1.1 to add or update a pinned dependency. It edits require:, installs sources into vendor/, and updates xu.lock. An explicit exact version is required; @latest is not accepted.

xu install installs dependencies already declared in the manifest. Both commands support --offline; use xu build . --frozen to build strictly against the existing lockfile. See Modules & Dependencies; the official packages repository provides 29 extension packages.

How do I use xu native to integrate C code?

xu native covers the native module workflow: xu native compile compiles C sources with interface metadata into a .a archive; xu native archive wraps existing object files with metadata; xu native pack bundles target slices into .xulib; xu native inspect and xu native extract inspect and extract slices.

Use .a for a single target, or .xulib to distribute interface contracts with multiple target slices. Pass the library directly to the build, for example xu build main.xu native/mylib.xulib -o app. Compiling C sources requires the corresponding C toolchain. See Native Modules & .xulib for full examples, or run xu native compile --help.

What operating systems and CPU architectures are supported?

Native multi-platform matrix: operating systems include macOS (Darwin), Linux, Windows (PE AOT), and WebAssembly; hardware architectures include ARM64 (Apple Silicon / AWS Graviton), x86-64 (Intel / AMD), LoongArch64, RISC-V 64/32, and Linux ARM32。

What is XACP?

XACP (Xu Agent Control Protocol) is the framed control channel for a hosted native program built with xu build --xacp and/or --xacp-port PORT. That build embeds discovery. ./app --xacp-help prints a machine-readable summary whose capabilities line is stdio, and which says whether TCP is enabled and which address it would bind. This replaces the earlier help-only discovery text.

#xacp (src/xacp) is the transport-neutral safety core: frame and XUN checks, permissions, and session lifetime. Importing #xacp does not install the startup control entry. Stdio and loopback TCP are runtime hooks inserted by the --xacp build. The launcher is xu xacp, which runs the sibling xu-xacp tool (module 0.1.1). Modes are inspect, run, debug, record, control, and connect. This behavior is from the language repository at 0.10.10-dev.1 (xu#23), not from the published {{xu_version}} SDK extract. See the CLI reference, the #xacp API, and the runnable example.

How do XACP stdio and loopback TCP differ?

stdio. Start the target with --xacp-stdio, or run xu xacp control <program>. The session owns stdin and stdout. Frames are --- !xacp … === followed by a newline. Business main does not run.

Loopback TCP. Build with --xacp-port N where N is 1..65535, then run <app> --xacp-tcp. The process listens only on 127.0.0.1:N. In another terminal, xu xacp connect PORT relays the same frames, one request and one response at a time. Port 0 disables TCP (tcp: disabled (port 0) in discovery) while leaving the stdio capability in place. Each accepted connection is its own session. Connections are handled one at a time; a failed peer ends that session and the listener stays up. Stdio exits when its session ends. The first control flag before -- wins. A normal start does not listen and does not read control stdin.

What does xacp.hello grant?

A control session starts with no permissions. The startup adapter validates xacp.hello (ver: !ver 1.0.0, monotonic id), begins the request, then calls enable_development() before finish_request, while the session is still STATE_NEW. That grants PERM_ALL. The success frame reports state: OPEN and permissions: development. Schema checks, session lifetime, native-resource disposal, and frame limits still apply.

Library dispatch() only completes hello. It does not grant development permissions, and enable_development() returns false once hello has finished and the state is STATE_OPEN. An optional token string is checked only as schema; the startup adapter does not treat it as an access secret. After development permissions are on, proc.status returns the real pid. proc.output and the UI ops (ui.tree, ui.screenshot, ui.input, ui.act, ui.record) are validated and then return not_implemented when no Screen or output adapter is registered.

How do xu xacp control and xu xacp run differ?

xu xacp run <program> -- args... starts the program so business main runs. The tool inserts an extra --, so a business argument named --xacp-help does not trigger discovery. debug prints --xacp-help first, then runs the same way. It is not a breakpoint debugger. record streams at most 1 MiB of stdout on Unix; stderr stays on the terminal. That file is not an XACP UI recording, and Windows record is still unavailable. inspect runs --xacp-help and accepts no business arguments. It does execute the target.

control starts --xacp-stdio, inherits the caller's stdin and stdout, skips business main, and accepts no business arguments. connect PORT does not take a program path. It relays frames to 127.0.0.1:PORT. User arguments for run, debug, and record must follow the tool's --.

What are the XACP security limits?

Point the launcher only at a trusted local executable. inspect executes it too. A validated hello on the startup channel grants development permissions, and control mode skips business main. There is no TLS and no bind address other than 127.0.0.1. There is no host timeout or forced stop if the target produces no output or does not exit; the caller has to impose one. UI Screen adapters are not wired on this channel, so tree, screenshot, input, act, record, and proc.output do not return live UI data. The generator allows hosted native executables only: it rejects libraries, shared objects, test harnesses, embedded targets, and --desktop.
