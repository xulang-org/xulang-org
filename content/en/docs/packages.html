Official External Packages

Official module: github.com/xulang-org/packages · SDK module version 1.0.2 · 29 service integrations and the shared transport package

The Xu {{xu_version}} SDK bundles the 1.0.2 drivers and their native source resources. The standalone 1.17.0 source adds the AI and GPU packages described below. Check the source version on each API page when selecting a dependency.

1. Select the SDK bundle or a fixed source commit

Place your project beside the extracted SDK and declare its bundled packages using a local source locator. Adjust the relative path if you installed the SDK elsewhere:

module: my_app
version: !ver 0.1.0
xu: !ver {{xu_version}}
require:
  "github.com/xulang-org/packages": file:../xu-v{{xu_version}}/packages

To fetch the source used by this SDK instead, select its full immutable commit:

require:
  "github.com/xulang-org/packages": git:https://github.com/xulang-org/packages.git@c16af7ca38dc31c289ca83670edf153f1f85f5f2

From your project directory, resolve and lock dependencies, then check and build:

xu install
xu check main.xu --offline
xu build main.xu -o my_app

Module versions and Git tags have separate roles: this bundle declares module version 1.0.2. The fixed source locator above selects the exact source independently of tag availability. Keep xu.lock with your application and consult modules and dependencies for frozen, vendor and proxy workflows.

2. Importing Packages in Source Code

Xu enforces an explicit namespace alias convention for all external packages: alias #full/module/path/pkg. This eliminates global namespace pollution and makes all external dependencies visible directly at the top of the file.

@main

// 1. Standard library modules have no alias; prefixed with #
#database/sql

// 2. External packages declare an alias and full repository path
mysql    #github.com/xulang-org/packages/mysql
redis    #github.com/xulang-org/packages/redis
postgres #github.com/xulang-org/packages/postgres

fn main() int {
    // Access APIs directly through the declared alias
    println("Drivers loaded successfully")
    << 0
}

Important: Do not write #mysql or #redis. External module imports require an explicit alias and full module path. Standard library imports and local package imports (such as #util) follow their own resolution rules. The integrations listed here belong to github.com/xulang-org/packages; other external modules have their own identities.

3. Hands-on Quickstart Examples

Example 1: Using the MySQL Driver with database/sql

The standard library database/sql provides connection pooling, transactions, and result row abstractions; the concrete MySQL driver is implemented by packages/mysql:

@main
#database/sql
mysql #github.com/xulang-org/packages/mysql

fn main() int {
    dsn := "root:123456@tcp(127.0.0.1:3306)/test_db?tls=false"
    $db := sql.open(mysql.driver(), dsn)
    db.ping() >>> (err) {
        println("Database ping failed: " + err.msg())
        << 1
    }
    println("Connected to MySQL successfully!")
    db.close() >>> (err) { << 1 }
    << 0
}

Example 2: Redis Client Operations

@main
redis #github.com/xulang-org/packages/redis

fn main() int {
    $client := redis.open("127.0.0.1:6379") >>> (err) {
        println("Redis connect error: " + err.msg())
        << 1
    }
    client.set("app_version", "demo") >>> (err) { << 1 }
    val := client.get("app_version") >>> (err) { << 1 }
    println("Key 'app_version': " + val)
    client.close()
    << 0
}

Example 3: Object Storage with S3 / MinIO

@main
s3 #github.com/xulang-org/packages/s3

fn main() int {
    $client := s3.open("http://127.0.0.1:9000", "access_key", "secret_key", "us-east-1")
    client.put_object("my-bucket", "welcome.txt", "Hello from Xu!", "text/plain") >>> (err) {
        println("S3 upload failed: " + err.msg())
        << 1
    }
    println("Object uploaded successfully")
    << 0
}

TLS paths: HTTPS business requests use the shared TLS connection path; their legacy manual fd pools remain plaintext. The default TLS configuration verifies certificates and hostnames; these source paths have not been exercised against every service here.

5. Boundaries & Production Builds

  • SQLite & Multi-Backend GPU Pure-FFI Architecture: The SQLite driver dynamically loads (dlopen) system libsqlite3 via pure-Xu sqlite_native (Windows automatically uses built-in winsqlite3.dll, overridable via XU_SQLITE_LIBRARY), eliminating static .xulib slices. CUDA and Vulkan use the same pure-Xu dlopen model (cuda_native / vulkan_native), while Metal GPU dynamically loads libxu_metal.dylib via metal_native (built with python3 metal/native/build.py, overridable via XU_METAL_LIBRARY).
  • Frozen Builds in Production: For immutable CI/CD deployment pipelines, commit the generated vendor/ directory and xu.lock to Git, then run xu build main.xu --frozen. This strictly forbids outbound network calls during build for 100% reproducible builds.

For more details on MVS resolution, checksum verification, and private proxies, see: Modules and Dependencies Specification and Native Modules Specification.

AI Package & Driver Known Boundaries

Production checklist: The following boundaries describe the packages v1.17.0 source; configure reverse proxies, external stores, or model checks accordingly before production rollout.

  • Hardware & host prerequisites across GPU backends: metal and llm_metal target Apple Silicon macOS only (building libxu_metal.dylib or overriding XU_METAL_LIBRARY); cuda_native requires host NVIDIA driver / NVRTC / cuBLAS libraries; vulkan_native requires a Vulkan 1.1 runtime. Meanwhile, xu/examples/llm_engine remains CPU multi-threaded (--threads N) rather than calling llm_metal or CUDA.
  • Built-in signing & pure-Xu SQLite loading: Since Xu v0.14.3, xu build embeds Mach-O LC_CODE_SIGNATURE ad-hoc signing directly (no manual codesign required); SQLite uses pure-Xu sqlite_native dynamic loading without .xulib compilation.
  • Vector store scale: PgVectorPool provides pooled concurrent connections via #database/sql (while single-connection PgVectorClient remains available for backwards compatibility); rag.SqliteVectorStore adds cache refresh helpers, though queries still scan loaded rows ($O(N)$ exact search — best under ~10k chunks; use PgVectorPool HNSW or QdrantVectorStore beyond that).
  • Gateway, A2A & guardrails operational notes: gateway supports Redis-backed shared state in v1.16.0+, though SSE failover still switches only before the first chunk arrives and cross-provider mapping targets common fields; a2a supports API key / custom auth hooks and SQLite persistence, while TLS termination still belongs in a front reverse proxy; pair guardrails.strict_policy with check_safety_openai against adversarial evasion.
